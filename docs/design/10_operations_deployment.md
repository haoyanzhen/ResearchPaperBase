## 合规与运行约束

### 外部学术数据库使用

- 系统必须遵守 arXiv、OpenAlex、Semantic Scholar、ADS 等外部学术数据库的 API 使用条款。
- 系统必须遵守各数据源的速率限制、认证要求、引用要求和禁止用途。
- 自动构建任务应具备失败降级和重试上限，避免因调度错误造成对外部 API 的异常请求压力。

### 隐私与数据保护

- 系统必须保护用户账号、Project、个人配置、研究对话、导出文件和通知收件人信息。
- 用户级 API key、系统级 API key、SMTP 密钥等敏感配置不得明文返回前端或写入日志。
- 管理员操作用户账号、系统级配置和密钥类配置时，应保留可审计记录。

### 版权与论文文件使用

- 系统下载、缓存、解析和导出论文 PDF 时，必须遵守论文来源和出版方的版权约束。
- 论文 PDF 导出、ZIP 打包和本地缓存应限制在用户有权限访问的 Project 范围内。
- 下载失败或版权限制导致无法获取全文时，应允许使用摘要作为降级文本，不应绕过来源限制。

### 成本与容量约束

- LLM API 月度预算、同时在线用户数、单次任务论文数量、Graph-RAG 检索性能和图谱构建性能以 [02_product_requirements.md](02_product_requirements.md) 的非功能需求为准。
- 部署方案应为 LLM 调用、外部 API 调用、PDF 存储、导出文件和任务日志设置容量上限或清理策略。

## 资源消耗与容量规划

### 估算基准

本节用于说明当前设计在硬件资源、网络和端口上的主要消耗来源。估算不是精确配额，而是部署规划的基准假设；真实消耗会受到论文去重率、PDF 是否可下载、导出保留周期、日志级别、向量分块策略和自动构建频率影响。

当前容量估算采用以下基准：

| 项目 | 假设值 | 说明 |
| --- | ---: | --- |
| 用户数 | 20 | 课题组级小团队部署 |
| 每用户 Project 数 | 10 | 每个用户维护多个长期研究课题 |
| 每 Project 论文数 | 100 | 指有效论文和关联论文的平均规模 |
| Project 总数 | 200 | 20 用户 × 10 Project |
| Project-Paper 关联数 | 20,000 | 200 Project × 100 论文 |
| PDF 平均大小 | 10MB/篇 | 按用户给定的“10GMB”理解为 10MB/篇 |

在最坏情况下，若 20,000 篇论文完全不重复且均成功下载 PDF，仅 PDF 原文约占用 `20,000 × 10MB = 200GB`。由于 `papers` 表采用全局去重，实际 PDF 存储可能低于该值；但不同研究方向差异较大时，应按最坏情况预留容量。

### 推荐资源档位

| 场景 | CPU | 内存 | 存储 | 适用范围 |
| --- | ---: | ---: | ---: | --- |
| 本地开发 / MVP | 2 核 | 4-8GB | 20-50GB | 单用户、少量 Project、少量 PDF 缓存 |
| 小团队试用 | 4 核 | 16GB | 300GB 起 | 约 20 用户、200 Project、20,000 篇 Project-Paper 关联 |
| 长期生产 | 4-8 核+ | 32GB+ | 500GB+ 或对象存储 | 长期自动构建、保留导出文件、真实向量库和图谱数据 |

`01_functional_requirements.md` 中的最低 4GB 内存、20GB 存储适合作为本地开发或最小 MVP 要求，不应作为上述 20 用户容量基准下的生产配置。

### 内存消耗来源

| 来源 | 占用特点 | 当前设计影响 |
| --- | --- | --- |
| FastAPI 后端进程 | 常驻内存 | API、认证、SQLAlchemy Session、配置缓存和请求响应对象 |
| Agent 流水线中间数据 | 任务运行时峰值占用 | 检索结果列表、候选论文、评分批次、AI 分析批次会在内存中处理 |
| LLM 请求上下文 | 单次调用临时占用 | 论文摘要、解析文本片段、对话历史、Graph-RAG 命中文段会进入 prompt |
| PDF 下载与解析 | 单篇峰值可能较高 | 当前下载后以 bytes 形式处理 PDF，单篇默认最大文件 50MB，解析时还会生成文本对象 |
| NetworkX 图谱 | 图构建期间明显占用内存 | 节点和边在内存中构建后序列化，作者共现边会随作者组合增长 |
| SSE 事件队列 | 按 Project 累积小额占用 | 每个 Project 队列最多缓存 200 条事件；Project 数较多时需监控 |

容量基准下建议生产内存以 16GB 为最低线，32GB 更稳妥。若后续接入真实 ChromaDB、增加并发 Agent 数或执行图谱全量重建，应优先提高内存或拆分服务。

### 存储消耗来源

| 来源 | 估算 | 说明 |
| --- | ---: | --- |
| PDF 原文 | 约 200GB | 20,000 篇 × 10MB，按完全不重复和全部下载成功估算 |
| PDF 解析文本 | 约 1-5GB | 当前每篇最多提取 100,000 字符，具体取决于论文页数和编码 |
| PostgreSQL 数据 | 约 2-10GB | 用户、Project、论文元数据、关系表、阶段记录、对话、综述内容、配置等 |
| 向量库数据 | 约 20-80GB | 取决于分块数量、embedding 维度、索引实现和是否保存原文片段 |
| 图谱文件 | 约 1-10GB | 取决于论文、作者、venue、概念、方法和边类型数量 |
| 导出文件与邮件附件 | 约 20-50GB 预留 | Project 导出、PDF ZIP、综述 DOCX/PDF、临时文件 |
| 日志与测试/诊断产物 | 约 10-30GB 预留 | 生产日志、错误快照、健康检查、E2E trace/screenshot/video |

在当前容量基准下，建议总存储至少 300GB 起步，推荐 500GB+。若 PDF 和导出文件长期保留，建议将 `STORAGE_DIR` 迁移到独立数据盘或对象存储，并为数据库、文件存储和备份预留彼此独立的容量。

### 网络与外部访问要求

| 网络对象 | 方向 | 要求 |
| --- | --- | --- |
| 用户浏览器到 Web 服务 | 入站 | 生产建议只开放 HTTPS；SSE 需要连接稳定但带宽较小 |
| 后端到 LLM Provider | 出站 HTTPS | 构建、评分、分析、深度研究和综述均依赖；需低丢包、可重试、可观测 |
| 后端到学术数据库 API | 出站 HTTPS | arXiv、OpenAlex、Semantic Scholar、ADS 等；必须遵守各数据源速率限制 |
| 后端到 PDF 来源 | 出站 HTTPS | arXiv PDF、Unpaywall 返回的开放获取链接；是主要带宽消耗来源 |
| 后端到 SMTP 服务 | 出站 SMTP/SSL/TLS | 常见端口 587、465 或 25；云服务器可能默认封禁 25 |
| 后端到 PostgreSQL/向量库 | 内网 | 生产应走内网，不应公网暴露数据库端口 |

在容量基准下，若一次批量下载 100 篇论文且 PDF 平均 10MB，单次 Construction Run 的 PDF 下载量约为 1GB。小团队试用建议至少稳定 50Mbps 下行；长期生产应根据每日自动构建 Project 数和 PDF 下载量评估带宽，并设置全局下载并发与每日下载上限。

| 用途 | 端口 | 暴露范围 |
| --- | ---: | --- |
| 后端 API / Swagger | 8000 | 本机或开发内网 |
| 前端 Vite Dev Server | 5173 | 本机或开发内网 |

生产建议：

| 用途 | 建议 |
| --- | --- |
| 对外访问 | 只公开 80/443，并通过反向代理转发到前端静态资源和后端 API |
| 后端 API | 仅内网监听，或由反向代理访问 |
| PostgreSQL | 仅内网访问，禁止公网暴露 |
| ChromaDB / 向量库 | 若独立部署，仅内网访问，并单独登记端口 |
| SMTP | 只允许出站到管理员配置的邮件服务端口 |

### 容量上限与清理策略

当前设计必须补齐以下运行策略，否则 20 用户容量基准下存储会持续增长：

- PDF 原文：按版权和团队需求决定是否永久保留；建议支持按 Project、时间、下载状态和引用状态清理。
- 解析文本：可随 PDF 保留，也可在向量化完成后按策略压缩或清理。
- 旧 Knowledge Version：active Research Session / Review Run 仍依赖时不得清理；无依赖后可按保留数量或保留天数清理。
- 向量库：应随 Knowledge Version 清理同步删除旧 collection / namespace / index。
- 图谱文件：保留最新版本和必要历史版本；全量重建产物应有替换和回滚策略。
- 导出文件：建议设置默认过期时间，例如 7-30 天，用户可重新生成。
- 日志与诊断产物：生产日志需要轮转；E2E trace、截图、视频不应长期保留在生产数据盘。
- 自动构建：应设置全局并发上限、每 Project 同时一个 Construction Run、每日最大自动构建 Project 数和每日最大 PDF 下载量。

### 监控阈值建议

| 指标 | 建议阈值 | 操作 |
| --- | --- | --- |
| 数据盘使用率 | 70% warning / 85% critical | 清理导出、旧版本、失败任务产物，或扩容 |
| PostgreSQL 连接数 | 70% warning / 90% critical | 限制并发任务，检查连接泄漏 |
| Agent 任务队列长度 | 持续增长 warning | 降低调度频率或提高 worker 资源 |
| PDF 下载失败率 | 单日 > 20% warning | 检查网络、来源限制和版权降级路径 |
| 外部 API 429/限流 | 任一数据源持续出现 warning | 降低速率、增加间隔或切换 API key |
| LLM 超时/限流 | 持续出现 warning | 降低并发、切换模型或配置备用 provider |
