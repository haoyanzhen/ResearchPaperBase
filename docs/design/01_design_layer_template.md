# Web App Design 分层参考模板

适用范围：包含用户管理、数据流、状态控制、异步任务或权限边界的 Web App。

使用方式：

- 简单项目可以只填写每层的“最小必填”。
- 复杂项目应补齐“建议补充”和“验收检查”。
- 同一个字段、状态、权限规则、接口响应，只允许有一个权威来源。

## 0. 文档控制

最小必填：

- 项目名称：
- 文档版本：
- 更新日期：
- 维护人：
- 关联文档：
- 当前权威来源：

建议补充：

- 变更记录
- 待决策项
- 已废弃设计
- 术语表

验收检查：

- 是否能判断哪个文档是最终契约。
- 是否能判断某个字段冲突时以哪里为准。

## 1. 产品与领域层

目标：说明系统做什么、不做什么、服务谁、核心业务对象是什么。

最小必填：

- 产品目标
- 用户角色
- 核心实体
- 功能清单
- 明确非目标

建议补充：

- 关键使用场景
- 业务边界
- 领域术语
- 优先级

验收检查：

- 一个新开发者能否在 10 分钟内理解系统边界。
- 是否能判断某个需求属于本期还是未来扩展。

## 2. 信息架构与用户流程层

目标：说明用户从哪里进入、怎么完成任务、如何退出异常状态。

最小必填：

- 路由结构
- 导航结构
- 核心用户旅程
- 页面进入条件
- 空态、加载态、错误态入口

建议补充：

- 用户首次使用流程
- 被拒绝访问流程
- 任务中断和恢复流程
- 移动端流程

验收检查：

- 是否能画出每个核心功能的页面路径。
- 是否能判断一个按钮在什么状态下可见、禁用或隐藏。

## 3. 状态机与业务流程层

目标：说明系统状态如何变化、谁能触发变化、失败后如何恢复。

最小必填：

- 核心状态枚举
- 状态流转图或表
- 状态触发条件
- 非法状态切换
- 重试、取消、暂停、恢复规则

建议补充：

- 幂等规则
- 并发控制
- 异步任务模型
- 调度策略
- 补偿策略

验收检查：

- 是否能判断任意操作前后的状态。
- 是否能处理重复点击、网络重试、任务失败、并发请求。

## 4. 数据模型层

目标：定义数据结构、关系、约束、删除语义和一致性要求。

最小必填：

- 数据表或对象模型
- 主键和唯一约束
- 外键或归属关系
- 软删除/硬删除规则
- 字段含义和枚举

建议补充：

- 索引
- 迁移策略
- 数据保留策略
- 文件存储
- 多存储一致性

验收检查：

- 是否能从数据模型判断数据归属。
- 是否能判断删除一个用户、项目或资源会影响哪些数据。

## 5. API 契约层

目标：定义前后端通信的稳定协议。

最小必填：

- Base URL
- 认证方式
- 统一响应结构
- 错误结构
- 接口列表
- 请求/响应示例

建议补充：

- 分页、排序、筛选规范
- 文件上传/下载规范
- SSE/WebSocket/流式响应规范
- 版本兼容策略
- OpenAPI 生成规则

验收检查：

- 前端能否只按 API 文档开发。
- 后端能否用文档生成契约测试。
- 错误处理是否可统一封装。

## 6. UI 与交互层

目标：定义页面布局、组件行为、视觉规则和交互反馈。

最小必填：

- 页面列表
- 页面线框
- 核心组件状态
- 表单校验
- 加载/空/错误/禁用状态

建议补充：

- 响应式断点
- 设计 token
- 可访问性要求
- 动效规范
- 权限态展示规则

验收检查：

- 是否能实现所有页面状态，而不是只实现正常路径。
- 是否能判断权限不足时是隐藏、禁用还是显示错误。

## 7. 权限与安全层

目标：定义谁能看、谁能改、凭什么改，以及敏感数据如何保护。

最小必填：

- 角色定义
- 权限矩阵
- 数据归属规则
- 登录态处理
- 敏感字段脱敏

建议补充：

- 管理员边界
- Token 失效策略
- 密钥加密
- 审计日志
- 防枚举策略
- CSRF/CORS 策略

验收检查：

- 是否能判断任意接口的访问主体和授权条件。
- 是否能防止用户看到或修改他人数据。

## 8. 质量、测试与可观测层

目标：定义如何发现问题、定位问题、证明系统符合需求。

最小必填：

- 单元测试范围
- 集成测试范围
- E2E 关键路径
- 错误码
- 日志字段

建议补充：

- 健康检查
- 诊断端点
- 结构化错误信封
- 契约测试
- 性能基准
- 告警规则

验收检查：

- 是否能定位一次失败发生在哪一层。
- 是否能自动验证核心用户旅程。

## 9. 运维、部署与演进层

目标：定义系统如何运行、升级、恢复和演进。

最小必填：

- 运行环境
- 环境变量
- 依赖服务
- 启动顺序
- 备份恢复

建议补充：

- Docker/Compose/K8s
- 数据库迁移
- CI/CD
- 日志采集
- 资源容量
- 版本升级策略

验收检查：

- 新机器能否按文档部署。
- 数据库升级失败时是否能回滚。

## 10. 追踪矩阵

目标：确保需求能落到实现契约和测试。

最小必填：

| 需求 | UI | API | 数据 | 状态 | 权限 | 测试 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FR-001 | | | | | | | 待补 |

验收检查：

- 每个需求是否至少有一个 API 或 UI 入口。
- 每个高风险需求是否有测试覆盖。
- 每个缺失项是否有人工确认状态。
