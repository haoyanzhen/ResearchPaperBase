# Domain 附录：知识库并行构建与版本更新

文档版本：v1.8
更新日期：2026-10-16  
依据文档：[功能需求](01_functional_requirements.md)、[Domain Core](02_domain_core.md)  
定位：Domain Core 的组成部分，定义知识库并行构建的业务对象、不变量、默认行为、确认边界和冲突裁决；不规定数据库、API、队列或锁的实现。第 1–10 章共同构成现行领域规则；第 10 章依据 2026-10-16 人工采纳的 1A、2A、3A、4B、5A、6B、7A 决策生效。

## 1. 目标与适用边界

项目持续吸收新知识，用户正在进行的研究保持稳定。新知识是否纳入已有研究，由用户根据变化与影响决定。固定旧版本是正常科研选择，不是需要消除的错误。

本附录不改变 Project 生命周期、权限分类、Review 终稿默认接受规则，也不将 P1 通用重跑、P2 协作授权或历史版本回退提前为 P0。并行保护必须在已有功能实施时成立；更新影响分析、协作接管等能力须在对应应用设计中明确范围，未实现时不能展示为可用能力。

| 构建候选版本 | ConstructionRun 内的未发布知识 | ConstructionRun 内尚未发布的候选知识集合；可预览，不属于正式研究可读取的版本 | FR-026 |

| 入库预览确认 | 候选入库决策 | 对具体候选内容、范围、风险和修订状态的决策；不对后续实质变化自动有效 | FR-017, FR-026 |
| 固定文献范围选择 | 继续使用绑定版本的用户决定 | 用户明确继续使用绑定版本的研究选择；保留检索截止时间与版本标识，不反复催促更新 | FR-018 |
| 版本变化清单 | 发布版本之间的变化事实 | 两个发布版本之间新增、修正、排除、来源变化和降级范围的事实说明 | FR-018 |
| 更新影响结果 | 指定版本与研究修订的影响分析 | 基于明确的新旧版本及研究内容修订形成的分析结果；未验证的关联只能称“可能相关” | FR-018 |
| 证据风险提示 | 独立于历史知识的风险说明 | 带来源和时间的撤稿、更正或解析错误提示；独立于历史知识内容，不能静默改写原证据或结论 | FR-018, FR-031, FR-033 |
| 新版本采用关联 | 原研究与新对象的采用关系 | 记录原研究对象、用户确认的目标版本及新会话/新版综述的关系；不迁移原对象身份 | FR-018 |

### 2.2 Knowledge 不变量

- KnowledgeVersion 固化 ConstructionRun 会修改并发布的全部可读知识内容，包括 ProjectPaper 关联与状态、ProjectMaterial 关联与状态、DocumentAsset、DocumentProcessingState/MaterialProcessingState 的可用文本来源、PaperAnalysis、MaterialAnalysis、向量索引、Graph 节点与边、引用定位和同步状态。
- P1 数据表和 P2 多媒体可作为 ProjectMaterial 入库，但默认不进入 Graph-RAG KnowledgeVersion；未参与版本的资料不得被标记为可检索证据。
- KnowledgeVersion 只能在关系库入库、向量同步和 Graph 创建/更新/重建完成后发布；Graph 未完成、失败或仍有待续连 ConstructionCheckpoint 时，不得发布新的 KnowledgeVersion。
- 基线失配的自动尝试失败退出、不等待用户；后续调度可在仍有效的自动更新授权下独立创建最新基线的新 Run，不得将旧尝试改绑或沿用过时确认。
- Project 默认 KnowledgeVersion 只更新到最新成功发布版本。
- 所有 ConstructionRun 发布尝试（包括首次执行、恢复、重试、重连和重跑）必须校验候选基线与发布时 Project 最新已发布版本一致；首次构建要求两者均无版本。不一致时拒绝发布并保留诊断，手动场景由用户明确改走最新基线的新构建；自动场景的后续调度可按有效授权独立新建 Run，不得自动改绑、合并或覆盖较新版本。
- ResearchSession 和 ReviewRun 创建时默认绑定 Project 当前默认 KnowledgeVersion；绑定后不得被系统静默改写。
- 新 KnowledgeVersion 发布后，active ResearchSession / ReviewRun 不被中断，不被强制切换，已完成内容不自动改写。
- 用户可继续使用或明确固定旧版本文献范围；旧版本依赖是正常科研状态，不得视为必须解决的冲突。固定后不反复催促更新，但重要证据风险仍须提示。
- 多个实例依赖旧 KnowledgeVersion 时，系统必须逐项识别对象、状态、绑定版本和采用新版本的可用操作；不得用全局“已刷新”状态代替各自依赖。
- 常规新 ConstructionRun 启动时默认以 Project 最新成功发布版本为基线并明确记录；旧研究依赖不阻止构建，不要求先迁移依赖或额外确认最新基线。无已发布版本时执行首次构建。
- D01 自动更新基线授权已决：用户启用自动更新，即授权在该配置范围内基于最新已发布版本持续构建；此授权不包含迁移旧研究、覆盖人工内容或绕过权限。AutoConfirmationPolicy 仅处理本轮低风险等待点。
- 旧版本依赖不得隐式作为新 ConstructionRun 的写入基线；发布必须保持单写入者、完整可见和已发布资产隔离。输入冻结、待纳入修订、确认失效及保留例外见本附录第 3、5、7 章。
- 引用跳转必须尊重引用产生时绑定的 Project、KnowledgeVersion 和 Evidence；论文、Project 资料、文段、文件或 Graph 节点缺失、越权、过期或版本不匹配时只能进入安全空态。
- ConstructionRun 失败时不得产生新的 KnowledgeVersion；未发布中间写入、断点和临时文件按[运行恢复附录](02-04_run_recovery_appendix.md#4-construction-断点与清理)清理。

### 2.3 资产纳入与图谱边界

- `candidate_sources` 不参与 KnowledgeVersion、引用、向量化或 Graph 构建；重复来源的保存承接[资产入库附录第 4 章](02-03_construction_assets_appendix.md#4-检索与候选处理)。
- [资产入库附录第 5 章](02-03_construction_assets_appendix.md#5-手动补充与资产边界)所定义的 P0 Project 资料支持范围可参与 KnowledgeVersion 构建。
- P1 数据表资料默认不得标记为参与 KnowledgeVersion 构建；P2 多媒体的知识构建能力后续扩展；资产入库与使用范围承接[资产入库附录第 5 章](02-03_construction_assets_appendix.md#5-手动补充与资产边界)。
- 从当前 Project 移除论文关联经一次风险确认自动受理移除型 Construction，只影响成功发布的后续版本；不得删除全局论文身份、破坏旧版本引用或影响其他 Project。
- 从当前 Project 移除 ProjectMaterial 经相同风险确认和移除型 Construction，只影响成功发布的后续版本；不得破坏旧版本引用或影响其他 Project 的资料或文件资产。
- PaperAnalysis 的候选入库确认承接[资产入库附录第 6 章](02-03_construction_assets_appendix.md#6-文本处理与分析确认)；手动和自动 ConstructionRun 中确认后的 PaperAnalysis，只有随 KnowledgeVersion 发布后才能作为正式深研和综述上下文使用。
- MaterialAnalysis 的候选入库确认承接[资产入库附录第 6 章](02-03_construction_assets_appendix.md#6-文本处理与分析确认)；手动和自动 ConstructionRun 中确认后的 MaterialAnalysis，只有随 KnowledgeVersion 发布后才能作为正式深研和综述上下文使用。
- 手动 ConstructionRun 入库前必须展示即将写入的有效论文、有效 Project 资料、跳过项、失败项、摘要降级项、不参与知识构建项和风险提示；未确认入库预览时不得写入 Project 知识库、向量库或图谱。自动 ConstructionRun 可由 AutoConfirmationPolicy 确认低风险入库预览，遇到高风险项不得静默入库，也不得等待用户响应；能跳过则跳过，能降级则降级，能局部失败则局部失败，只有无法保证不污染已发布知识库、向量库或图谱时才整体失败。
- ConstructionRun 写入 ProjectPaper、ProjectMaterial、DocumentAsset、向量项、图谱项和 KnowledgeVersion 相关状态失败时，必须保留可诊断失败原因和一致性边界；失败写入不得发布新的 KnowledgeVersion，也不得污染已发布知识版本。具体自动重试次数和后台清理编排由应用层定义。
- 图谱创建、增量更新、重建和修复只能由 ConstructionRun 触发；ResearchSession、ReviewRun 和只读知识资产入口不得触发图谱写入。
- 首次成功 ConstructionRun 触发图谱创建；之后的手动 ConstructionRun 默认只触发本次新增或变更论文和 P0 Project 资料所需的图谱增量更新，只有用户在 Construction 面板维护入口明确选择重建时才触发图谱重建；自动 ConstructionRun 作为无人值守维护窗口，在自动检索、入库和向量同步达到可发布条件后，应对当前 Project 图谱执行重建或修复性重建；若本次及上次成功重建后无知识库变更，可跳过重建。

### 2.4 读取与采用接口

- ReviewRunBrief 必须绑定 ReviewRun 和 KnowledgeVersion；大纲生成、自审和章节撰写不得使用未绑定或其他 Project 的输入简报。
- 用户重跑 Review 生成新大纲、章节或终稿时，新版本只能使用单一绑定 KnowledgeVersion。
- 章节引用必须能映射到当前 Project 论文库或 Project 资料库，并绑定 ReviewRun 的 KnowledgeVersion。
- 章节正文中的引用必须来自该章节绑定 KnowledgeVersion 下可访问的论文、Project 资料、文段或 Graph 节点。
- PaperAssetDetail 只能展示用户有权访问的 ProjectPaper、DocumentAsset、已确认 PaperAnalysis 和可映射 GraphEntityRef；缺失任一部分时不得拼接其他 Project 或其他 KnowledgeVersion 的上下文补齐。
- MaterialAssetDetail 只能展示用户有权访问的 ProjectMaterial、DocumentAsset、已确认 MaterialAnalysis 和可映射 GraphEntityRef；缺失任一部分时不得拼接其他 Project 或其他 KnowledgeVersion 的上下文补齐。
- ProjectGraphView 必须绑定 Project 和 KnowledgeVersion；默认展示 Project 当前默认 KnowledgeVersion，来自 ResearchSession 或 ReviewRun 的引用跳转必须尊重其绑定 KnowledgeVersion。
- ResearchSession 或 ReviewRun 的引用跳转到知识资产面板时，必须校验引用的 Project、KnowledgeVersion、论文/资料、文段和 GraphEntityRef；越权、缺失、过期或版本不匹配时只能进入 KnowledgeAssetEmptyState。
- ConstructionRun 正在写入新的 KnowledgeVersion 时，知识资产面板可继续展示已发布的默认版本或当前 Run/Session 绑定版本，并提示默认知识库正在更新；不得读取未发布半成品作为可用资产。
- 无可访问的已发布 KnowledgeVersion 时不得创建新的 ResearchSession；空版本是合法已发布版本，允许创建并沿用无证据交互，不得伪造引用或暗中改用历史版本。
- 每个 ResearchTurn 基于该 Session 绑定的 KnowledgeVersion 执行 Graph-RAG 检索，并保存 ResearchRetrievalContext。
- ResearchSession 的 KnowledgeVersion 绑定不可原地刷新，即使无运行回复亦不得改绑；采用新知识须由用户按 FR-018 确认目标版本并创建关联新会话。原会话及运行回复继续使用原版本，携带的历史结论只能作为待复核背景，不得冒充新版本已验证证据。
- 引用展示缺失、过期、越权或版本不匹配时，只能降级 ResearchCitationContext 或进入安全空态；不得改写原 ResearchMessage 或 ResearchTurn。
- 无可访问的已发布 KnowledgeVersion 时不得创建新的 ReviewRun；空版本允许创建，明确无知识证据，沿用低支撑提示与确认，不注入其他版本证据。
- ReviewRun 采用单 KnowledgeVersion 设计；同一 ReviewRun 的输入简报、大纲、章节和终稿必须使用同一个绑定 KnowledgeVersion，不支持同 Run 内混合版本生成。
- 用户“基于最新文献创建新版综述”属于 P0：确认目标版本、继承输入和完整重生成范围后，从头生成新的 ReviewRun 或具有独立绑定和内容身份的新运行结果；原 Run 不改绑，原稿、人工修改和已接受成果保留。人工修改可作为明确标记的参考输入，不自动继承其确认状态。

FR-018 版本采用专用操作为 P0：Research 创建关联新会话，Review 保留原用户主题并绑定用户确认的新 KnowledgeVersion 从头生成新 Run/独立运行结果，保留原对象和结果；不得修改原绑定。该操作不把通用重跑或其他 P1 控制提前为 P0。通用重跑不得借用该路径静默采用最新版本；Construction 通用重跑如原基线已不是最新版本，不得据此发布覆盖最新成果，应显式改走基于最新版本的新构建。

### 2.5 不可变逻辑快照与资产复用边界

2026-10-16 人工确认：KnowledgeVersion 保存完整、不可变的逻辑快照；物理上仅复用不可变资产修订。以下为现行边界，不要求为每版复制全部文件，也不授权跨 Project 共享私有资产或调整产品分期。

- 区分资产身份、资产修订、版本成员关系：同一论文身份可对应多个正文、分析和派生产物修订；版本清单必须确定实际使用的修订，不能只指向“当前资产”。清单及其引用闭包在发布后不可原地覆盖；仅冻结清单而覆盖被引用文件、分块、向量或图谱不满足本规则。
- 完整逻辑快照包含论文/资料成员及发布状态、元数据、文本来源、文件、分块、分析、引用定位、向量视图和图谱视图。任何影响可读证据或检索范围的变化均创建新修订，并重验受影响下游依赖；这不授权直接修正已入库论文/资料内容，内容更改须先移除发布再新导入；正文未变不代表分块、模型或图谱产物可复用。发布时同步证明固化，发布后的故障、权限和风险作为独立运行信息，不重写历史知识事实。
- Research/Review 及其子任务、重试、恢复、分页、引用跳转始终携带原绑定版本。普通浏览仅在入口解析一次默认版本，后续读取使用已解析版本。禁止在链路中再次解析 latest，或因旧证据缺失改用新版本补齐。版本一致不承诺 LLM 多次生成逐字相同。
- 版本内检索、排序、图谱遍历与引用解析只使用该版本可见资产；不能全局检索取 top-k 后才过滤版本，不能只过滤图谱起点。可复用物理内容，不可扩大逻辑可见范围。权限、撤稿风险和可用性仍按当前事实检查，版本绑定不是永久访问凭证。
- 新版本发布只改变后续新对象的默认选择；运行中的读取不被切换。清理必须同时保护持久依赖和在途读取，并与取得读取资格互斥裁决；不能靠先查一次引用数保证安全。明确授权删除/撤权仍按第 7 章执行，失去依赖的任务明确失败而非混读。
- 首版实现选择：文件、正文等不可变资产允许复用；向量索引和图谱按候选/已发布版本隔离。接口不暴露具体 namespace 或存储结构；后续共享实现必须通过同等一致性验收后替换，不能降低这些边界。

资产粒度与提交/回收协议见 [07 第 5.1–5.3 节](07_data_persistence.md#51-资产原子单元与修订闭包)；服务读取契约见 [06 第 3.1 节](06_agent_knowledge_services.md#31-版本读取与存储适配契约)。保留期限、容量阈值和跨 Project 联合引用不在本次决策范围。

本文恢复/重试语境中的“原输入”指该次执行所绑定的最后有效输入修订；初始冻结快照仍保留，不能借恢复修改输入、配置或基线。显式返回检索是独立用户动作，仅按第 3.2 节在筛选等待点追加词。

### 2.6 引用有效性与跨版本重新引用

引用有效性分开判断：身份/版本一致、当前可访问性、定位完整性、证据风险及对论断的支持情况。可解析、存在引用或数量充分，不等于结论正确；本节不新增自动语义裁决；人工采纳 R1-A 后不提供严格引用覆盖率/阈值，学术规范与建议式审查见领域主文第 8.1 节。

- 历史引用绑定原 Project、KnowledgeVersion、资产及不可变证据修订；正文片段绑定具体文本修订，图谱引用绑定具体视图及节点/边。URL、DOI、标题、文件名或页码单独不能标识证据。
- 采用新版本时，旧引用作为待复核背景保留。目标版本须重新核验成员、修订与定位，并形成目标版本绑定的新引用；即使两版复用同一不可变内容，也不能仅修改旧引用的版本号。新引用可记录来源引用关联，不能沿用原人工确认或声称旧结论已得到新证据支持。不存在目标成员时显示“目标版本未纳入”，不能用来源版本补齐。
- 新引用形成属于现有 Research/Review 生成与引用保存流程，不新增自动迁移、自动跨版匹配端点。已生成引用不可重新赋予其他修订；正文发生变化后的支持性复核须绑定具体论断内容修订与证据修订，未执行则明确未复核。
- 同一论文身份、相同内容校验值、甚至同时拥有两个 Project 的访问权，都不使来源 Project 的私有文件/分析/图谱成为目标 Project 的成员。来源 Project 可在独立授权上下文查看，不注入当前研究；需要纳入目标 Project 时仍走既有接收与 Construction 发布流程。跨 Project 联合检索/混合引用、自动复制私有资产不在本次范围。

| 事实 | 读取与展示 |
| --- | --- |
| 历史版本证据可读且定位完整 | 正常打开原版本并标注历史范围；旧版本本身不构成失效 |
| 后续版本排除论文/资料 | 不影响旧版成员和引用，不等同物理删除 |
| 撤稿、更正、解析风险 | 可访问时原证据与有来源/时间的风险并列；不重写原结论 |
| 临时存储故障 | 暂时不可用，可重试同一引用；不标永久失效、不改用最新版 |
| 文件访问凭据过期 | 重新鉴权获取同一修订的访问能力；引用身份不因凭据过期失效 |
| 版本/修订/定位校验失败 | 拒绝返回冒充原证据的内容，保留安全诊断 |
| 撤权、删除或永久缺失 | 按当前权限安全拒绝；仅在允许披露范围说明原因，不泄漏其他 Project 的存在或内容 |

风险与可用性是带检查时间的动态投影，独立于不可变引用记录；无风险记录仅表示未记录风险，不保证已全面核查。自动风险发现渠道不在本节新增。持久依赖和回收沿用 §2.5/第 7 章。

### 2.7 按任务选择版本的规则

版本选择服务于研究目的；“最新”只表示发布顺序，不是质量评分。P0 使用现有版本列表、知识资产入口及 FR-018 采用路径，不新增智能推荐排序或章节影响分析。

| 目的 | 默认版本与动作 |
| --- | --- |
| 新建研究/综述 | 默认当前最新已发布版本，说明发布和范围事实；可显式选择可用历史版本 |
| 继续既有研究/修订综述 | 原对象绑定版本；查看其他版本不改变绑定 |
| 核查历史结论/引用 | 成果原绑定版本及原证据；查看最新版是独立浏览 |
| 纳入更新知识 | 查看与原版本的变化，明确目标版本后创建关联新 Session/新版 Review |
| 固定文献范围 | 保持选定版本；不承诺该版本已满足某个日期截止或完整检索要求 |

版本摘要区分：发布事实（时间、成员数量、文本来源构成）、本次构建的检索输入与执行事实、累计版本成员范围、当前访问/可用性和风险。累计版本可能继承旧范围并含手工资料，本次检索数据源/时间窗不等于整个版本完整覆盖；revision_only 不产生新的检索截止事实。发布时间、检查时间、检索执行时间和论文发表日期互不替代。未知值显式未知，不推算为零或用发布时间填充。

版本卡片显示 Project、版本 ID、发布时间、成员数、文本来源构成、范围摘要、默认标记；对象绑定/已固定标签来自当前对象而非版本全局属性。查看变化时固定 from/to，知识范围排除与撤稿分开，未分析具体结论影响时明确未分析。无法使用的已授权版本展示原因，不提供无效启动动作；无权限版本不得泄漏摘要。

用户已选中/预览具体版本时，提交必须携带其 ID。期间发布更新不替换选择、不使旧选择仅因不再最新而失效；目标不可用则明确失败。只有调用者未指定目标的默认创建，才在创建事务解析最新并返回实际绑定。界面展示具体目标后不得省略 ID。采用路径沿用现有确认，不新增通用二次确认。

## 3. 构建默认行为

1. **取得构建资格。** 同一 Project 同时仅一个 ConstructionRun 占构建槽，running、paused 和等待人工处理的占槽运行均不允许另一个写入者。构建槽不阻止授权用户保存配置、提交待纳入材料、进行研究或编辑综述。重复调度不得重复创建本轮构建；后续请求可登记，但登记不等于启动或取得写资格。
2. **确定并冻结输入。** 常规新构建在实际开始时使用最新已发布版本；首次构建无版本基线。记录本轮输入与配置，排队期间保存的请求不预先固定一个过时发布基线。之后修改配置默认下轮生效；之后上传或在其他页面提出修订默认进入待纳入清单，须说明归属。
3. **隔离处理。** 候选下载、解析、分析、索引及图谱处理不改变现有研究所见内容。用户在本轮构建入库确认受理前明确修正候选内容时，记录变更，使受影响下游结果失效并重新处理；不视为偷偷变更启动配置。待纳入修订在构建开始纳入后，也必须保留来源和冲突处理记录。
4. **确认候选。** 手动构建保留各阶段确认和入库预览，展示新增、修正、排除、跳过、失败、降级及冲突。入库确认受理后锁定候选内容，不开放编辑；外部排除决定或依赖变化使原发布依据无效时不得继续按旧确认发布，按第 3.3 节处理冲突。无关配置保存不使本轮确认失效。
5. **发布检查。** 发布前检查权限、项目可写状态、构建写资格、人工决定冲突及完整可用性。所有发布尝试，包括首次执行、恢复、重试、重连和重跑，均须校验候选基线与此时 Project 最新已发布版本一致；首次构建要求两者均无版本。不一致则拒绝发布并保留诊断，手动场景由用户明确发起最新基线的新构建，自动场景由后续调度按有效授权独立新建 Run，不得自动改绑、合并或覆盖较新成果。构建期间新增人工排除或同一目标修订不能被旧候选覆盖；未解决的条目按人工确认或自动策略处理。与本轮无关的待纳入修订可以保留到下一轮，但必须仍显示未发布。
6. **完整发布。** 只有成功 ConstructionRun 可以发布。关系知识、索引、图谱和引用范围满足同一候选版本的发布条件后，正式读取整体切换到新版本；不存在一部分已经作为最新版本可读而其他部分仍是旧版的状态。允许复用未变化资产，不要求全量复制。图谱重建、修复同样只能在该写入边界内进行。
7. **无变化成功。** 已有版本且完成完整核验、知识无实质变化时，按第 10.4 节以 succeeded/no_change 收尾，关联核验既有版本，不发布、不切换默认版本、不发送升级提示或空邮件；零新增或来源失败不等于无变化。
8. **失败与结束。** 失败、取消、恢复或清理不得污染已发布版本，也不得把 Project 默认版本回退至启动基线。清理仅处理该运行所属且不再需要的未发布产物，不删除独立保存的待纳入修订、人工内容或其他任务资产。暂停不按失败超时隐式释放槽；显式取消或重跑先终止旧写资格，再交接，迟到结果无权发布或改写状态。

自动更新的 D01 裁决：用户启用自动更新即授权在该配置范围内，以最新已发布版本持续构建；旧研究依赖无需逐次确认，不阻止自动更新。此授权不包含研究改绑、人工覆盖或权限扩张。AutoConfirmationPolicy 只可确认低风险项，或跳过、降级、局部失败并记录待处理事项；无法避免污染时整体失败，不无限等待用户。人工排除不得因自动检索再次命中而撤销，人工确认不得自动沿用到修改后的内容。

基线失配的旧自动尝试应失败退出，不等待用户，也不得自动变更该尝试的基线；后续调度可在有效自动更新授权下独立创建基于最新版本的新 Run。此独立新建不属于恢复旧 Run，不复用其过时确认。手动旧运行改走新构建仍需用户明确选择。

普通重复检索承接[资产入库附录第 4 章](02-03_construction_assets_appendix.md#4-检索与候选处理)的跳过规则；已发布论文与资料需要补全文本、修正元数据或分析时，须先成功移除再新导入，不再接受既有成员的内容修订，也不建立重复活动 ProjectPaper。人工排除决定持续有效，不得因再次检索命中自动撤销。备选资料来源仅作为独立候选线索；更换已入库主来源也须移除后新导入，处理确认并发布后才进入后续版本，其余资格限制见第 2.3 节。

### 3.1 构建槽不变量

- paused ConstructionRun 继续占用项目构建槽，手动新建和自动调度均不得创建第二个占槽运行；暂停不等于释放写入排他资格。
- paused ConstructionRun 持续保有该 Project 的独占构建资格；手动新建和自动调度均不得创建第二个占槽运行。暂停、进程重启、超时或锁租约失效均不得隐式释放，也不得以自动归档或失败超时清理代替显式决定。
- 显式继续恢复同一 ConstructionRun 实例并沿用原槽，不创建新 Run。显式取消先使旧实例及其 Worker 失去写资格，再将其取消并清除占槽；随后才允许其他 Run 取得资格。取消后的清理按[运行恢复附录](02-04_run_recovery_appendix.md#3-重试重连与重跑)执行。
- 显式重跑保留旧实例及其历史；先使旧实例及其 Worker 失去写资格，再创建新的 ConstructionRun 实例并将原槽交给新实例。交接未完成前不得启动新写入者；旧 Worker 的迟到结果不得发布或改写状态。执行机制由后续 `05` 细化，本节不指定实现锁方案。

### 3.2 同 Run 返回检索与纯修订构建

API-D01 A 已采纳：初始冻结快照不可变；返回检索形成新的输入修订和来源链，保留原 Run、知识基线及配置，记录变更原因和受影响候选/阶段/确认。旧输入修订的执行资格失效，迟到结果不得写入新修订；受影响结果重新计算与确认，人工保存内容保留并标示依赖失效，不静默删除。候选需要重做时回到准备中，已发布版本不变。仅手动筛选等待阶段允许追加已确认检索词；原词、来源、时间范围、总预算、配置与基线不变，只使用剩余额度，新候选重新去重/筛选并保留已有人工决定。入库确认后禁止返回检索；修改范围或额度须新建构建。失败恢复只能恢复最后有效输入修订，不能借恢复新增修改或换基线。

API-D07 A 已采纳：常规检索和纯补充/纯修订是同一 ConstructionRun 的输入模式。纯补充/修订至少包含一个已确认新增/重新导入补充或明确关联移除，不启动新检索，仅执行输入需要的解析、分析、索引或排除处理；已确认且未变的结果不要求无意义重做，相关确认和发布完整性仍须满足。取得槽后固定最新基线，待纳入修订的 base_asset_revision 与当前基线冲突时拒绝或要求显式修正，不能静默覆盖。

纯关联移除不要求 LLM 或数据源配置；需要解析/分析的输入按实际能力验证配置并冻结。本模式不提供任意发布或跳过人工确认能力；有变化按 published，无变化须完整核验后按 no_change。有意移除全部成员形成 published 空版本，空关系/索引/图谱视图保持完整一致；可浏览并新建 Research/Review，明确无证据，不暗中回退历史版本。失败/零检索结果不转换为清空成功。

### 3.3 关联移除、空版本与重新导入

2026-10-16 人工采纳 R3-A/R4-A，并明确论文与 ProjectMaterial 统一适用。

- 单条、批量和全部移除均展示范围、已知依赖及历史保留风险；旧引用依赖不阻止移除。一次确认自动受理仅移除的 revision_only Construction，显示待移除/排队/运行状态，成功发布后才从新版本移除，不即时隐藏正式成员或物理删除历史资产。
- 确认绑定具体成员集合与修订；排队新增成员不自动加入“全部”，目标内容或范围变化须刷新确认。无冲突按槽排队；已列明的冲突 Construction 在同次风险确认中获准安全终止，先撤销旧写资格再让槽。预览后新出现的冲突运行须刷新影响预览，不擅自取消；无关研究、综述及构建不终止。该确认可作为移除构建的入库决定，不对相同范围再要求重复确认。
- 失败/取消保持原默认版本和诊断；同意图重复请求返回已有结果，不重复发布。若目标已由其他成功移除完成，明确返回已完成事实，不伪造新变化；未完成请求不得丢失。
- 全部论文与资料均被明确移除时允许发布空版本并切换默认指针，结果是 published 而非 no_change；失败、零新增不表示主动清空。空版本可浏览、创建 ResearchSession/ReviewRun；显示无知识证据，保留既有无证据继续及低支撑确认，不伪造支持。用户也可显式选择可访问历史版本，系统不暗中替换选择。
- 论文与资料的项目元数据、文件/正文、解析文本、分析、评分/有效性自入库确认受理后锁定；已发布内容只读。权限、可用性、已知风险与推送状态是独立投影，可依既有规则更新。失败未发布保留人工草稿及诊断，P0 可新建构建准备候选，不新增原 Run 恢复入口；P1 恢复仍使用冻结依据。
- 更改已入库内容须先成功发布移除，再显式新导入；两次发布间该资产不属于最新版本，历史证据不受影响。保留全局 PaperIdentity 及 Project 逻辑身份，建立新入库修订/成员，不制造重复活动关联。当前版本仍有成员时拒绝新导入暗转内容修订；已移除时明确提示历史排除并确认重新纳入。自动检索不得恢复人工排除，显式新导入不继承旧人工确认，允许安全复用不可变字节但不以旧分析冒充新内容分析。

## 4. 版本发布后用户如何继续研究

| 场景 | 默认行为 | 采用新知识 |
| --- | --- | --- |
| 已有研究对话，包括跨越发布时间的一条回复 | 全部检索与后续追问保持原绑定版本 | 用户确认目标版本，创建关联新会话；原会话继续可用 |
| 运行中的综述、多章节撰写、审查 | 同一 Run 全部使用原绑定版本，保存人工内容 | 创建新版 ReviewRun 或独立绑定的新结果，从头生成 |
| 查看最新证据对旧章节的影响 | 独立分析，不直接改写章节 | 记录新旧证据及被评估章节修订，仅输出建议 |
| 普通知识浏览 | 新打开的项目知识浏览默认最新发布版本 | 已打开阅读上下文不强制跳转，用户可切换 |
| 历史引用跳转 | 使用当时版本、原文件及定位 | 查看最新版是独立操作，不替换旧引用 |
| 导出 | 固定发起时的稿件、引用、版本与附件范围，执行时仍校验访问权限 | 新版本不是导出前置要求 |
| 工作区恢复 | 恢复原对象、位置和草稿，展示更新摘要 | 不自动提交、迁移或重跑 |

新会话可以携带用户选定问题、上下文和历史链接；旧结论标记为待复核背景，不能当作目标版本已经验证的证据。新版综述至少保留原用户主题，明确继承哪些输入、完整重生成范围、成本和原稿保留位置；人工修改可以作为参考，但其确认状态不随文本自动继承。原稿和原 accepted 成果保留，新终稿仍遵守正文第 8 章的默认接受与显式拒绝规则。

**重跑不等于采用新版本。** P1 通用重跑使用原输入、配置和数据版本，保留原实例；P0 新版本采用是用户明确选择新证据后创建新对象/独立结果。Construction 按旧基线进行通用重跑若已落后于项目最新版本，不得发布覆盖最新成果，必须显式改走最新基线的新构建。恢复、重试也不得悄悄切换输入或基线；必要依赖不可用时给出诊断。

## 5. 确认与通知边界

| 处理方式 | 情况 |
| --- | --- |
| 需要用户明确决定 | 手动阶段及入库预览；采用新版本创建关联研究或新版综述；替换人工编辑/确认内容；不确定合并、实质文件替换；取消或接管他人构建；任意单条/批量/全部关联移除（同次说明历史保留及已列明冲突构建终止） |
| 说明或常规通知即可 | 发布成功；配置下轮生效；上传或修订未纳入；排队原因；构建失败或部分未纳入；新版本变化清单 |
| 显著风险提示，不自动重写 | 相关论文撤稿、关键更正、解析错误、人工确认依据发生实质变化；固定文献范围也不得隐藏这些提示 |
| 无需重复确认 | 旧研究继续运行；常规新构建默认最新基线；已授权自动更新；低风险自动处理；无变化检查 |

明确命名且显示后果的操作可构成用户确认，不要求重复弹窗。确认只能在已有权限内生效，不授予权限。未实现 P2 协作授权时，只适用 Owner 自用边界；后续接管必须有明确业务授权和影响预览，不能因为持有 access、是管理员或任务等待很久就自动取得他人任务处置权。

“新增文献”“项目内排除”“论文撤稿”“解析更正”必须区分。新文献通常提供轻量更新提示；撤稿、更正保留原研究记录并显著提示风险；依据变化的人工确认标记需要复核，但不能自动撤销用户判断或替用户下新结论。只有实际完成相应影响分析才能声称影响了具体结论。

## 7. 历史保留与访问例外

仍被保留的研究、综述或引用依赖的必要证据，不得自动清理。普通论文范围排除只影响后续版本，不等于物理删除历史文件。解除依赖后的保留期限由后续应用与存储设计细化。

用户明确授权的项目删除、私人资产清理及必须执行的删除义务，仍按现有权限与影响预览规则执行；不能以历史保留承诺阻止这些操作。撤权、删除或依赖不可用时，历史对象保留允许保留的状态和诊断，显示不可访问原因，不绕过授权、不重新公开文件，也不以新证据替换旧证据。已有下载或导出副本不保证随权限变化被收回。

## 10. 构建与知识版本状态机

> 本章依据 2026-10-16 用户明确采纳的 1A、2A、3A、4B、5A、6B、7A 转为现行规则。Run 状态名复用 [Domain Core 第 3.2 节](02_domain_core.md#32-通用状态)，不改变 P0/P1/P2 分期。重试、重连、断点校验、临时产物清理引用 [运行恢复附录](02-04_run_recovery_appendix.md)，本章只定义状态转换及竞争裁决，不另立恢复算法或清理窗口。

### 10.1 状态对象与职责

| 对象 | 职责 | 不代表什么 |
| --- | --- | --- |
| ConstructionRun | 一次有身份、输入与基线的构建业务过程；使用 `draft/queued/running/waiting_user/paused/succeeded/failed/cancelled` | 不是一个进程；任务失败不使已有知识失效 |
| 执行 attempt | 某个后端运行单元的一次执行，归属 Run；记录尝试身份、执行结果、诊断和当次写资格 | attempt 局部成功不是 Run 成功；旧 attempt 不能以当前 Run 仍运行为由继续写 |
| 候选版本 | Run 内未发布的知识修订；使用“准备中、待发布、已发布、已废弃” | 预览与人工确认不等于正式可读；“待发布”不是不可撤销的许可 |
| 已发布 KnowledgeVersion | 成功发布形成的完整、可追溯证据边界；沿用第 2.2 节固化范围 | 不随 Run 的后续通知、临时文件清理失败而变为失败 |

候选内容自入库确认受理起即锁定；候选版本的“已发布”表示它已成为相应 KnowledgeVersion 的来源，更不能再编辑同一候选修订。候选记录与发布版本是否使用同一存储实体由后续持久化设计决定，不在本领域规则中预设。

“最新版本”是 Project 的默认版本关系，“固定文献范围”是研究选择，“仍被引用”是依赖关系，“存在撤稿提示”是风险属性；均不增加为版本生命周期状态。归档与删除沿用既有生命周期、权限和保留规则，不在本章增加 ConstructionRun 执行状态。

**Run 失败与 attempt 失败的区分：**

- 单个 attempt 失败先保留该 attempt 的诊断。若按已授权策略仍可在相同 Run 输入与基线下重试，且 Run 仍有有效构建槽，可以记录新 attempt，Run 保持 `running`；不可伪造原 attempt 成功。是否可以重试及次数由 [02-04 第 3–4 章](02-04_run_recovery_appendix.md#3-重试重连与重跑)及后续应用策略决定。
- 手动运行需要用户处理可恢复问题时转 `waiting_user` 并保槽；自动运行不得进入该状态。明确暂停后仅转 `paused`，不能以 attempt 失败或超时暗中终结暂停占槽。
- 本轮不能继续执行、当前重试策略耗尽或触发不可继续条件时，Run 转 `failed`，先使现有 attempt 失权再释放槽；候选不发布。后续清理和可恢复窗口严格承接 02-04。
- **允许已 failed 的原 Run 通过受控重试/重连提交到 `queued`，重新取得槽后用新 attempt 继续。** 前提是未放弃恢复、候选未废弃或清理、原输入与基线不变、依赖可用、恢复条件成立；重连还必须通过 02-04 的断点校验。失败 Run 既有未发布中间写入只可用于可信断点续连；retry 不能任意复用它们作为已成功结果。排队和执行前都不得假定原槽仍属于它。尝试历史与曾经失败的诊断不得被覆盖。
- `succeeded/cancelled` 不恢复为运行态；显式通用重跑创建新 Run。改变构建基线或运行配置必须新建 Run；手动返回检索的显式输入修订为 API-D01 A 已批准例外，见第 3.2 节；除此之外改变启动输入仍须新 Run；同轮入库确认受理前的候选修订按第 3 章处理，不视为暗改启动配置。断点不可用时不得重连。Run 仍为 running 且保槽时，按原输入独立执行的局部 attempt 可依 02-04 受控 retry；已 failed 且留有未发布中间写入的 Run，仅可依可信 ConstructionCheckpoint 续连，不得将从头重建包装成原 Run 的局部 retry。必须从头重跑时创建新 Run。旧基线已过时则不得恢复发布，改走最新基线新构建。



### 10.2 构建运行状态机

槽与 Worker 写资格分开判断：槽属于 Run；单次执行仅凭有效 attempt 资格写入；`paused/waiting_user` 保槽但不准后台任意推进。`queued` 一律不占槽，可能等待其他 Run，也可能等待执行资源。保槽运行的内部重试、暂停继续和人工继续均不转 `queued`。

以下是允许的全部状态改变（R16 为保持状态的后续动作）；组合来源每个成员分别适用。未列出的不同状态转换均拒绝；同状态重复请求按第 10.5 节处理。正常新建从 `draft` 开始，自动请求也沿用相同审计链。

| ID | 转换 | 触发者与条件 | 构建槽 | 验收 |
| --- | --- | --- | --- | --- |
| R01 | 新建 → draft | 授权用户或有效自动调度；仅建立请求，不冻结过时基线 | 无 | S01 |
| R02 | draft → queued | 用户提交或调度提交；输入请求有效；提交校验失败保留 draft 并说明原因 | 无 | S01 |
| R03 | queued → running | 应用调度；执行资源就绪且成功取得唯一槽，重新检查权限与可写性；常规新构建冻结最新基线及输入；通用重跑沿用原实例输入、配置和版本并校验基线仍为最新，恢复执行亦保持并校验原基线 | 无 → 有 | S02 |
| R04 | queued → failed | 应用检查发现权限、项目可写性、原基线等不可执行条件；记录诊断；暂时资源忙或尚未轮到执行保持 queued | 无 | S03 |
| R05 | running → waiting_user | 仅手动 Run；有效阶段确认或可修复问题，需要用户决定；当前后台不得绕过等待点 | 保留 | S04 |
| R06 | waiting_user → running | 有权用户提交有效决定/修复；校验目标修订及继续条件 | 保留 | S04 |
| R07 | running → paused | 有权用户显式暂停且所有异步运行任务已实际暂停；暂停请求尚未完成时仍显示原状态及待处理请求 | 保留 | S05 |
| R08 | waiting_user → paused | 有权用户显式暂停；全部异步任务已暂停，保留未解决等待项与暂停来源 | 保留 | S06 |
| R09 | paused → running | 显式继续，暂停来源为 running；原 Run、原槽，续执行资格校验通过 | 保留 | S05 |
| R10 | paused → waiting_user | 显式继续，暂停前未解决等待项仍存在；不能以继续操作代替确认 | 保留 | S06 |
| R11 | running → failed | 当前执行不可继续或策略耗尽；保留诊断并撤销旧 attempt 写资格 | 有 → 无 | S07 |
| R12 | waiting_user → failed | 不可恢复约束失效而无法继续；普通有效人工等待没有本章新增的超时失败规则，不借用 02-04 对已 failed Run 的清理窗口 | 有 → 无 | S07 |
| R13 | failed → queued | 获授权的 retry/reconnect、恢复资料仍可用、未放弃恢复或清理、候选未废弃且原输入/基线未改；新的 attempt 在重新获槽后执行 | 无 | S08 |
| R14 | draft / queued → cancelled | 有权用户或具备既有业务依据的系统取消；不得以取消别人请求扩张权限 | 无 | S09 |
| R15 | running / waiting_user / paused → cancelled | 显式有权取消或已生效管理命令的受影响执行终止（API-D04 A）；先撤销所有旧执行写资格，再完成取消及释放；显式重跑按表后定向交接，paused 不因超时自动触发 | 有 → 无 | S10 |
| R16 | failed → failed（后续动作） | 有权用户明确放弃恢复；保留失败状态与原诊断，记录放弃及清理状态，关闭原 Run 恢复资格；清理承接 02-04，不转 cancelled | 无 | S11 |
| R17 | running → succeeded | 仅第 10.4 节 published 或 no_change 成功决定；阶段完成和通知成功均不能单独触发 | 有 → 无 | S12、S28 |

暂停继续遇到权限、资产、基线问题时拒绝继续并提供诊断，不用后台自动 `paused→failed` 释放槽；显式取消或重跑仍按第 3.1 节执行。旧 paused Run 显式重跑后记为 cancelled，记录“被显式重跑替代”原因与新 Run 关联；该操作将 R15 与新实例的 R01–R03 作为一个原槽定向交接整体：旧 Worker 先失权，交接期间原槽不向第三方开放，新实例处于 queued 时自身尚不占槽；安全交接完成后新实例成为 running 并独占原槽。不能先把槽公开释放再让新实例普通排队，也不能让新旧实例同时持槽；交接完成前保持可诊断的交接记录，不借进程重启或超时将槽交给第三方。 若新 Run 创建确定失败，或新 Run 在接管前确定进入 failed（R04）/cancelled（R14），且旧执行者失权已确认，则已无有效接管者：关闭定向交接预约并记录原因，释放保留资格供其他申请；保留旧 Run 的 cancelled、被重跑替代原因及新 Run 关联（如已创建），并保留创建失败或新 Run 失败/取消诊断，不恢复旧 Run。创建/准入/取消或旧执行者失权结果不明时先查证；未证实失权不得释放，不能以超时或进程重启推定交接失败并让槽。该收尾只处理已显式重跑且无有效接管者的交接，不使 paused Run 自动让槽。

API-D04 A：显式归档/删除/清理已生效时，受影响的非终态 Run 按 R14/R15 安全取消并记录管理原因；资格先撤销，旧 Worker 不得成功提交，再释放槽。已终态保持原结果，失败 Run 不转 cancelled，必要清理单独记录。仅执行准入时发现无有效管理取消记录的不可执行条件仍按 R04；这一区分不改变暂停超时不能让槽的规则。

失败恢复使用 R13，而不是 `failed→running`；在排队中被另一 Run 发布新版本后，R03 必须拒绝旧基线并走 R04。暂时性 attempt 失败、阶段推进和发布前技术检查发生在 `running` 内，不另设 Run 状态。

### 10.3 候选版本状态机

“待发布”意味着以下准备事实均已成立：当前候选修订和范围明确；手动预览确认或合规低风险自动策略决定绑定此修订；人工冲突已有处理结论；关系知识、文本、引用定位、向量及图谱满足第 2.2–2.3 节完整性要求；不存在待续连 ConstructionCheckpoint。按第 2.3 节，手动入库预览确认必须先于候选向 Project 知识库、向量库及图谱的隔离写入；自动运行采用该节允许的策略决定。确认完成仍不等于索引、图谱及其他完整性条件完成，不能仅因此进入待发布。

| ID | 转换 | 条件与观察 | 验收 |
| --- | --- | --- | --- |
| C01 | 无候选 → 准备中 | Run 实际获槽开始处理；仅候选区可见 | S13 |
| C02 | 准备中 → 待发布 | 上述准备事实全部成立，记录具体候选修订及检查依据；不改变默认版本 | S13 |
| C03 | 待发布 → 准备中 | 外部相关决定变化、受影响投影失效、发布检查发现完整性不足，或 Run 失败后需要恢复重验；使受影响结果失效，依据变化撤销旧确认，不开放已锁定候选内容编辑；单纯权限临时变化不伪造内容修订 | S14 |
| C04 | 待发布 → 已发布 | 当前 Run 为 running，且第 10.4 节发布重验与联动决定成功 | S12 |
| C05 | 准备中 → 已废弃 | 取消、明确放弃，或 02-04 规定的清理生效；不可再作发布候选 | S15 |
| C06 | 待发布 → 已废弃 | 同 C05，或第 10.4 节 no_change 成功决定成立并记录“核验无变化”；发布若已先完成则不能废弃该发布成果 | S15、S28 |

同一准备中候选仅在入库确认受理前可以积累内容修订；每次确认都绑定所审阅修订，受理后不得因退回准备中重新开放编辑。无关配置修改、未纳入材料或浏览操作不触发 C03。恢复原 Run 只能按 02-04 的可信断点要求续用未废弃候选。已废弃或已清理候选不得复活、复用或被包装成原 Run 的局部 retry；需要从头重建候选则新建 Run。仍 running 且保槽的局部 attempt 重试不改变上述失败 Run 续连边界。

已发布不能退回准备中、待发布或已废弃。新知识、纠正或排除通过后续构建发布新版本；资产访问撤销和授权删除承接第 7 章，不用改写版本生命周期表示。

### 10.4 成功结果与发布联动

发布时再次检查：当前权限及 Project 可写性；唯一槽与当前 attempt 写资格；候选修订与确认一致；人工决定冲突；基线与项目最新已发布版本一致（首次均无版本）；关系知识、索引、图谱、引用和同步完整性。待发布记录只证明曾满足准备条件，不能替代当前校验。

ConstructionRun 的 succeeded 有两类互斥结果属性：`published`（发布新版本）与 `no_change`（完整检查成功、知识无变化），不是新增状态。失败、取消和未完成检查均不能取得这两类结果。

published 具有一个可判定先后的业务提交点。在该点，Run 成功且结果为 published、候选已发布、新 KnowledgeVersion 可读、Project 默认指向该版本、当前执行写资格终止及构建槽释放作为一个整体成立；外部不能观察到任意子集已成功而其余尚未成立。不预设跨存储实现事务；准备期可构建隔离资产，但未提交的内容不可作为正式知识读取。只有当前合法发布者能够作出此决定，重试不能重复产生版本。

发布前失败不产生新的可读版本；提交结果不明时先查证该发布决定，不盲目取消、回滚或再发布。发布后通知、邮件或非必要临时文件清理失败分别记录、按所属任务规则处理，不将 Run 改为 failed，不撤销版本、不回退默认指针。后续较新构建以 published 成功后默认指针自然指向较新版本，不影响先前成功的真实性。

**无变化成功（no_change）：**

- 必须已有可用的已发布基线；首次构建没有既有版本时不能 no_change，符合发布条件的首次成功走 published。
- 按本轮冻结的输入、检索范围和已纳入修订完成检查，记录检查时间、范围、来源完成情况、跳过/降级/失败及诊断。零新增论文不等于无变化；来源失败或未完成造成的“没有查到”不能证明 no_change。任何使本轮无变化结论无法成立的缺失都不得成功收尾，按既有失败或待处理路径处理。
- 对第 2.2 节全部可读知识范围核验：论文/资料纳入及排除、正文来源、分析、引用定位、索引和图谱等均无实质变化；仅运行时间、执行日志或不改变可读知识的技术检查不同，不产生新知识版本。既有资产复用也必须验证可用性，不以跳过重建代替完整性核验。
- 候选仍须经 C02 达到待发布；当前修订的人工确认或合规自动决定有效。no_change 成功提交点重新校验权限、Project 可写性、原基线仍为最新、唯一槽与当前 attempt 写资格、人工决定及完整性。不得用 no_change 绕过发布级检查、未解决冲突或失败恢复条件。
- 同一提交决定使 Run succeeded、结果为 no_change、候选经 C06 已废弃并记录“核验无变化”、结果关联本次核验的既有版本、执行写资格终止及槽释放一致成立。不创建 KnowledgeVersion、不改变 Project 默认关系、不把候选标已发布，也不声称既有版本由本 Run 发布。废弃仅关闭候选资格，实际临时资产清理遵守 02-04；必要检查、确认和诊断记录保留。
- 不发送空邮件或知识升级提示；可在运行历史展示“检查成功，无知识变化”及本轮范围，不影响独立撤稿/更正风险提示。后续日志或清理失败不逆转该成功结果。
- no_change 与 published 均使用可查证、可防重的成功决定；响应不明时先查证，不盲目再执行或宣布取消。no_change 后另一 Run 发布新版本不改变本次核验事实。


### 10.5 取消与恢复竞争

本节只定义状态裁决，恢复条件、断点可靠性及清理流程引用 [02-04 第 3–4 章](02-04_run_recovery_appendix.md#3-重试重连与重跑)。

- published 或 no_change 成功决定先成立：保留 succeeded 及相应结果；随后取消返回已完成，不产生 cancelled，不回退默认版本或改写核验关联。只发出取消请求或界面点击更早，不能证明取消已生效。
- 取消先完成写资格撤销并成立：published 与 no_change 成功提交均必须拒绝；即使旧 Worker 已做完候选资产、手持旧确认或返回成功，也不得发布或改写取消状态。不得同时成立“该 Run 已取消”和“该 Run 成功”（含 no_change）。
- 重复确认、取消、继续、重试和发布请求须关联同一意图与对象修订；重复请求返回已有决定，不重复创建 attempt、占槽或版本。独立的新重试意图可创建新 attempt，但同一执行单元不能被重复推进。
- 重试/重连只能使用同一 Run 原输入与基线，且旧 attempt 已失权。运行资格不能因进程重启、租约到期或客户端重连自动交给另一 Run。
- failed 原 Run 重新取得槽前后均检查恢复资格；过时基线拒绝发布并保留诊断，手动明确新建最新基线 Run，自动场景按第 3 章由后续调度独立新建。不得原地改绑或沿用旧确认。
- 入库确认受理后的内容编辑一律拒绝。人工排除与发布竞争按同一裁决边界排序：排除先生效则撤销已授权冲突执行者写资格，旧候选不得完成；发布先完成则保留成功事实，对最新目标范围重新核验移除确认，不扩大授权。移除仍须新 Construction 发布，不能让用户误以为已进入刚发布版本。

| S27 | 暂停槽与排队请求 | 多次调度/超时/进程重启不释放暂停槽；继续沿原槽；显式重跑时旧先失权，交接期间第三方不得抢占；queued 新实例尚未占槽，交接完成后新实例 running 唯一接管；旧 Run cancelled 并记录被重跑替代原因/新 Run 关联；通用重跑新实例保持原输入、配置和版本，过时基线不得执行发布；新 Run 创建确定失败、准入失败或接管前取消且旧失权已确认时关闭预约并释放给其他申请，保留旧取消和新失败/取消诊断，不恢复旧 Run；旧失权未证实或创建/准入/取消结果不明时先查证，不因超时释放 |
| S28 | R17、C06，无变化成功 | V1 基线上完成全范围核验且知识无变化：Run succeeded/no_change，候选已废弃并记核验无变化，结果关联 V1，无新版本/默认切换/升级提示/空邮件，槽释放；首次无版本不得 no_change |
| S29 | no_change 条件缺失 | 分别测试零新增但正文/分析/索引/图谱有变化、来源失败导致没有查到、未完成检查、权限撤销、基线过时、确认失配、资产损坏：不得以 no_change 成功；有实质变化且满足门槛者走 published，其余保留诊断 |
| S30 | no_change 与取消/重复/响应丢失 | 成功决定先成立则取消返回已完成；取消先失权则禁止 no_change；重复或响应丢失只查证同一成功决定，不补发版本或重复释放别人的槽；后续清理失败不改成功 |
| S31 | attempt 失败与 Run 失败 | 可按策略局部重试时 Run running 保槽、创建新 attempt 并保留旧诊断；策略耗尽或不可继续才 Run failed 失权释放；已 failed 且有中间写入无可信断点不得恢复，已放弃或清理者不得复活 |
