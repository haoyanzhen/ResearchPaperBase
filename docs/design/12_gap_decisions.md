# 设计缺失项选择与建议

状态：待人工确认
生成日期：2026-04-28
依据：`11_design_audit.md` 与重整后的 `00_index.md`

本文档不直接修改最终契约，只列出需要人工确认的选择项。确认后再回写 `07_api_contract.md`、`06_data_model.sql`、`04_information_architecture_ui.md`、`02_product_requirements.md`、`09_quality_observability.md`。

## D-001 统一 Project / Stage / Task 状态模型

问题：

- `06_data_model.sql` 使用 `projects.status = idle/running/paused/error/archived`。
- `07_api_contract.md` 示例仍出现 `draft/completed/cancelled`。
- `/tasks` 与 `stage_records` 关系不清。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 以 `06_data_model.sql` 为准，删除 API 中 `draft/completed/cancelled`；`tasks` 只是 `stage_records` 的聚合视图 | 改动最小，但导出/图谱重建等非 stage 任务表达较弱 |
| B | 新增 `tasks` 表，Project 状态只表示项目级锁，Task 状态表示每个异步任务生命周期 | 数据模型更清晰，但需要迁移和更多 API |
| C | 扩展 `stage_records.status` 支持 `cancelled`，继续不建 `tasks` 表 | 容易把 stage 和 task 混在一起，不建议 |

建议：

- 短期选 A，快速消除 schema/API 冲突。
- 中期若导出、邮件重发、图谱重建、调度任务增多，再升级为 B。

建议确认项：

- 是否允许新增 `tasks` 表。
- 取消任务是否统一写 `projects.status = idle`、`stage_records.status = failed` 并记录 `error.code = ERR-VAL-CANCELLED`。

## D-002 REST 统一响应结构

问题：

- `07_api_contract.md` 顶部定义 `code/data/message` envelope。
- 具体接口示例大多返回裸对象。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 所有 REST 成功和失败都返回 `{code,data,message}` | 前端封装简单，文档需大规模修订 |
| B | 成功返回裸对象，失败返回统一错误对象 | 更贴近 FastAPI 默认风格，但前端成功响应类型不统一 |
| C | 写操作返回 envelope，读操作返回裸对象 | 规则复杂，不建议 |

建议：

- 选 A。该项目功能多、错误诊断重，统一 envelope 更利于前端和契约测试。

建议确认项：

- SSE 事件是否不包 envelope，继续使用事件专属 payload。
- 文件流下载是否例外，不包 envelope。

## D-003 错误码体系

问题：

- `07_api_contract.md` 使用数字错误码。
- `09_quality_observability.md` 使用 `ERR-*` 字符串错误码。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 统一使用 `ERR-*` 字符串码，REST/SSE/DB error 都一致 | 需要替换 `07_api_contract.md` 数字码 |
| B | REST 用数字码，SSE/诊断用 `ERR-*` | 前端需要两套错误处理 |
| C | 同时返回 `code` 数字和 `error_code` 字符串 | 信息完整但冗余 |

建议：

- 选 A。`ERR-*` 更可读，已被 QA 错误信封和测试设计采用。

建议确认项：

- REST envelope 中 `code` 字段是否允许字符串。若保持数字 `code`，则新增 `error_code` 字段。

## D-004 SSE 认证方案

问题：

- 浏览器原生 `EventSource` 不支持自定义 Authorization header。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 使用 HttpOnly Cookie 认证 SSE | 浏览器原生 EventSource 可用，但要补 CSRF 策略 |
| B | 使用短期 stream token 查询参数 | 改动较小，但 URL 泄露风险需控制 |
| C | 用 `fetch` + ReadableStream 替代 EventSource | 可携带 Authorization header，前端解析 SSE 成本更高 |

建议：

- 深度研究对话已适合 C，因为它本来就是 POST 流式响应。
- 构建/综述进度流建议选 B 或 A。若系统当前以 JWT Bearer 为主，短期选 B 更容易落地。

建议确认项：

- 是否接受 Cookie 认证体系。
- stream token 有效期建议 60~300 秒，且只能用于指定 project 和 stream 类型。

## D-005 构建阶段是否允许跳过

问题：

- `02_product_requirements.md` 禁止跳过。
- `07_api_contract.md` 和 `04_information_architecture_ui.md` 允许 `skip`。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 删除 skip，所有阶段必须执行 | 与验收一致，最安全 |
| B | 仅允许跳过部分非关键阶段，如邮件发送 | 需要逐阶段定义补偿 |
| C | 保留全部 skip | 数据一致性风险高，不建议 |

建议：

- 选 A。邮件发送阶段本来是自动阶段，不需要用户 skip。

建议确认项：

- 是否允许用户“取消整条流水线”作为 skip 的替代。

## D-006 深度研究图谱重建入口

问题：

- ADR/spec 定义深度研究只读图谱。
- API/UI 提供深度研究图谱重建。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 删除深度研究中的重建 API 和按钮 | 保持只读边界 |
| B | 将重建移动到构建模式或管理员维护页 | 仍保留能力，但需任务锁 |
| C | 保留深度研究重建，但只允许管理员 | 仍破坏模式语义，不建议 |

建议：

- 选 B。知识图谱重建是维护能力，不是深度研究对话能力。

建议确认项：

- 手动重建是否允许项目所有者触发，还是仅管理员触发。

## D-007 文件上传契约

问题：

- 手动添加论文示例使用 base64。
- 通信设计声明上传使用 multipart。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 统一使用 `multipart/form-data` | 标准、适合大文件 |
| B | DOI/arXiv/URL 用 JSON，PDF 用 multipart | 语义清晰，推荐 |
| C | 全部使用 JSON base64 | 简单但不适合 PDF |

建议：

- 选 B。

建议确认项：

- 单文件大小上限。
- 批量上传最大数量。
- 是否支持后台解析进度。

## D-008 PostgreSQL 与 ChromaDB 一致性策略

问题：

- 文档要求强一致同事务，但 ChromaDB 不参与 PostgreSQL 事务。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | Outbox 模式：PostgreSQL 先写待同步记录，后台同步 ChromaDB，状态可观测 | 最现实，但不是严格同步提交 |
| B | 应用层补偿：先写 ChromaDB，再写 PostgreSQL，失败时删除 ChromaDB | 实现简单，但异常边界多 |
| C | 放弃强一致，改为最终一致并提供修复任务 | 简单，但与现有设计目标不一致 |

建议：

- 选 A，并把“强一致”修订为“关系库记录与向量同步状态强可观测；对检索只暴露 synced 数据”。

建议确认项：

- 是否允许新增向量同步状态字段或 outbox 表。
- Graph-RAG 是否只检索同步成功的论文。

## D-009 文件存储和导出生命周期

问题：

- 有 PDF、text、GraphML、Excel、ZIP、DOCX/PDF 导出，但无存储生命周期。
- 只有全局论文身份与基础元数据可能跨 Project 复用；Project-Paper 关联、历史 Run/Session、PDF、解析文本、向量索引、GraphML 和任务临时产物应按 Project 私人资产处理。
- 用户需要可选择清理 Project 私人资产，否则长期自动构建会导致存储无限增长；导出产物应默认保留并由导出生命周期单独管理。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 本地文件系统，按 user/project 分目录 | 简单，适合单机 |
| B | 对象存储，DB 只存 key | 更适合生产，但部署复杂 |
| C | DB 存二进制 | 不建议，影响 DB 体积 |

建议：

- 开发和小团队部署选 A，预留对象存储抽象。
- 文件与向量/图谱 namespace 必须以 user/project 或等效 Project 私有边界组织，便于用户按 Project 清理私人资产。
- 导出产物使用独立目录、对象前缀或生命周期标记，默认不随 Project 私人资产清理删除。

建议确认项：

- 导出文件保留多久，以及用户是否可单独删除某个导出结果。
- Project 软删除后是否自动提示清理私人资产，或仅提供手动清理入口。
- 私人资产清理是同步执行、异步任务，还是先标记待清理后由后台 worker 回收。
- 下载链接有效期。

## D-010 管理员权限边界

问题：

- 管理员配置和账号管理清晰，但是否能读取用户项目内容不清。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 管理员只管理账号和系统配置，不能读取用户项目内容 | 隐私更好 |
| B | 管理员可以读取所有项目用于运维支持 | 运维方便但需审计 |
| C | 管理员默认不能读，临时授权后可读 | 最安全但实现复杂 |

建议：

- 选 A。科研数据敏感，默认不授予管理员内容读取权。

建议确认项：

- 是否需要“用户授权管理员协助诊断”的临时授权机制。

## D-011 综述版本管理模型

问题：

- 当前 `review_outlines`/`review_chapters` 不足以支持完整文章版本 diff/rollback/merge。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 降级 FR-024，只支持大纲版本和章节当前版本 | 改动小，但不满足原需求 |
| B | 新增 `review_versions`，保存完整文章快照和元数据 | 满足版本需求，需迁移 |
| C | 每次章节修改都创建版本 | 历史完整但数据量大 |

建议：

- 选 B。完整文章版本应独立于大纲版本。

建议确认项：

- diff 粒度是 Markdown 文本 diff，还是章节级结构 diff。

## D-012 推荐点赞与审核

问题：

- `recommendations.like_count` 无法防重复点赞。
- 内容审核缺少 API 和日志。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 新增 `recommendation_likes` 和审核字段 | 最完整 |
| B | 只用 IP/session 限制点赞 | 不可靠 |
| C | 暂时移除点赞功能 | 简化 MVP |

建议：

- 选 A；如果追求 MVP，可先选 C，保留查看和发布。

建议确认项：

- 推荐内容默认公开还是审核后公开。
- 是否支持取消点赞。

## D-013 UI 设计系统和响应式范围

问题：

- 当前 UI 是 ASCII 线框，缺少视觉和响应式规范。

可选方案：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 只支持桌面端，补齐加载/空/错误/权限态 | 最小可行 |
| B | 同时支持桌面和平板，移动端降级提示 | 中等成本 |
| C | 完整响应式移动端 | 成本最高 |

建议：

- 选 B。科研工作台复杂，手机完整体验价值有限，但平板和窄屏需要可用。

建议确认项：

- 最小支持宽度。
- 是否需要暗色模式。
