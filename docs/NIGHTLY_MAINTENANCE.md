# 项目每日整理规则

文档版本：v1.0
更新日期：2026-10-23

## 1. 授权与入口

用户于2026-10-23授权：将整理规则写入项目，手动试跑并检查后，每天Asia/Shanghai凌晨03:00执行；后续工作改为重新整理任务拆解文档，保证边界清晰、覆盖完整。授权包含文档维护、证据核对、任务规划及文档检查，不包含自动执行规划中的业务任务。

每次从本文件、[AGENTS](../AGENTS.md)、[项目状态](PROJECT_STATUS.md)、[设计索引](design/README.md)、[实施入口](IMPLEMENTATION_ENTRY.md)、[任务模板](../tasks/example.md)、[任务拆解清单](workorders/preimplementation_design_tasks_2026-10-21.md)开始，按变化读取具体任务与证据。工作目录固定为本仓库；先核对目录和Git身份，不能在另一副本上更新状态。

PROJECT_STATUS是当前进度唯一入口；任务单保存范围、执行及接受证据；任务拆解清单组织依赖和覆盖。01决定需求含义/分期，00决定架构，专题规则按设计索引定位。最新日期、最多重复次数或模型判断均不能替代人工裁决。

## 2. 每次执行

1. 读取上次成功记录与快照，记录本次时区、时间、HEAD、Git状态。核对已跟踪、未提交、未跟踪及删除文件；忽略依赖、构建产物和凭据。首次建立全量源文件基线；后续比较上次成功快照，不仅查看过去24小时提交。已有证据只读，按需核验摘要和来源，不重新打包历史证据。
2. 使用已有 `python3 scripts/delivery_snapshot.py create --directory docs/workorders/evidence/<唯一运行ID>/before` 保存入场源文件；该目录必须不存在。快照包括未提交/未跟踪源文件，不递归打包证据目录。失败运行不可成为下次成功基线。无需变化时可仅在聊天记检查结果，不创建每日空报告或递增文档版本。
3. 对每个变化追踪“需求/批准规则→任务范围→实际产物→执行日志→人工接受”。分开记录设计、实现、自动验证、人工接受。旧测试注明原日期/基线；受影响产物漂移时标明待复验，不沿用旧通过结论。声明与实际冲突时只暂停依赖部分，登记待核验。
4. 最小同步PROJECT_STATUS、当前入口、任务当前衔接说明及派生引用。历史工作单、接受记录、失败日志和快照保留原义，不批量改成今天的状态。规范真实冲突列出问题、证据、选项、建议和受阻范围；不改变业务语义、权限、人工保护、版本绑定或产品分期。不自动执行缺陷修复、代码/机器契约变更、迁移、部署、Git提交/推送或外部通信。
5. 按第3节重新整理任务拆解，继承稳定ID和授权，不重复建同义任务；不输出仅有三个模糊目标的替代清单。
6. 写入前重新读取并比对所读文件内容。共享工作区有并行变化时重新核对、合并最小补丁；不能覆盖读后变化。无法稳定核对时跳过该文件并记受影响部分，继续独立项。禁止reset、clean、stash及恢复他人文件。避免两次整理重叠；检测到同类运行未结束时退出本次并报告，不中断他人工作。
7. 执行第4节检查、自审差异后，以唯一运行ID保存报告、实际命令/检查输出、修改前后差异、输入/输出SHA-256与成功标记。对修改文件再次检查无漂移后保存after快照；成功记录必须指向实际快照。报告可追加调度配置结果，但历史证据不重写。下一轮同时检查未完成/失败记录，避免遗漏。

## 3. 任务拆解完整性

- 保留A01–A10设计接缝、B01–B08工程类型、H01–H03决定边界；它们不是业务实现全量任务，也不是执行授权。
- 按01现行FR及其子条目/验收条件、非功能要求、02不变量、08安全、09验收族和10运维要求核对覆盖。每项必须有唯一主责任务或明确缺口、延期/待决定归属；交叉约束通过引用复用，不能复制并行的同义任务。
- 任务包含可观察结果、包含/排除范围、负责文件/写入所有者、输入输出、真实前置、授权、正向/拒绝/失败及适用并发/权限/版本/人工保护场景、完成条件和交接对象。阶段混合的FR必须按子条目拆分，不能整条推迟或提前。
- 每个开放TRACK必须映射到任务或缺口；每个A/B/H必须有边界。维护无归属、重叠、循环依赖、过大切片及缺验收清单。A05/A06对齐是定稿校验而不是循环硬前置；只阻塞实际消费缺失契约的工作。
- 区分“全量索引有归属”“逐需求任务拆解完成”“测试覆盖完成”。FR目录级覆盖不能冒充子条目完整覆盖。无法当轮完成的细拆必须列出具体需求范围、承接任务与缺少字段，保留开放状态；不以兜底B类条目宣称完成。
- 清理任务拆解中的过时当前描述，但保留建单时假设。优先维护已有任务及真实审核缺陷的交接，不自行恢复延期选型或启动下一任务。

## 4. 检查与失败处理

文档维护检查所有修改/新增文件的本地链接和锚点、版本/日期、任务ID唯一性、硬依赖循环、FR/开放TRACK归属、当前状态与证据一致性、限定diff和空白。未跟踪文件同样检查。仅实际修改的版本文档递增v1次版本，无变化不改版本。

人工语义自审检查需求边界、接受范围、历史/当前分离、未授权工作和人类内容保护；文件存在或测试数量不等于覆盖。只改文档不运行无关应用测试。发现业务验证缺口登记原任务，不自动连接业务库、LLM、论文源或邮件；后续获授权测试遵守AGENTS隔离要求。

检查失败先修复本次文档维护引入的问题。业务原有缺陷、未授权依赖或真实规范冲突单列，不伪称修复。部分失败不推进成功基线，保留差异与失败原因，下次从最后成功记录继续核对。没有历史成功记录时做全量入场核对。

## 5. 交付与调度

有变化时在 `docs/workorders/` 新建或追加本轮独立报告，内容为：新增进展及来源、同步文件与原因、任务边界/覆盖变化、待核验或待决定、实际检查与未验证范围、快照位置。当前状态只汇总到PROJECT_STATUS，日报不复制全量台账。

定时执行使用Codex本聊天周期任务，每天Asia/Shanghai 03:00读取本文件最新规则。每日完成后在聊天提供简短整理结果；本地仓库可用需要电脑开机且Codex桌面应用运行。不要自行声称具有离线补跑能力；再次运行从上次成功基线覆盖遗漏变化。调度配置成功不等于未来定时触发已验证，首次实际触发须在结果中区分。
