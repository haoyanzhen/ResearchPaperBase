## 设计目标

实现课题组级的学术论文研究平台，以研究主题（Project）为核心单元，提供三种研究模式：

- **构建模式**：通过 Agent 工作流自动检索、筛选、下载、解析论文，构建课题的论文数据库底座
- **深度研究模式**：基于已有论文库，通过 Graph-RAG 检索与 LLM 进行对话式深度探讨，支持理论分析、技术讨论、实验设计等多种研究场景
- **综述模式**：由 Agent 主导，基于已有论文库自动撰写综述文章，支持用户分步审查与修改

系统成为科研人员安全、可靠、有用的学术研究信息基石。

## 数据总体设计

所有数据的顶层单元为**用户**；用户可以建立多个研究主题（Project），不同用户的 Project 互不相关，每个 Project 内部独立。

**论文存储采用两层结构**：

- `papers` 表全局共享：同一篇论文（以 DOI / ArXiv ID / 标题去重）在数据库中只存储一份，多个 Project 通过 `project_paper_relations` 关联表引用同一条论文记录，避免重复下载和重复存储
- 评分、推送状态等**课题相关属性**存储在关联表中，同一篇论文在不同 Project 中的评分和推送状态相互独立

> **设计意图**：全局去重是为了降低存储成本和 API 用量；评分独立是因为同一篇论文对不同课题的价值不同。两者不矛盾，是有意分层的设计。

## 框架设计

总体框架为**基础层 + 多模式**：基础层始终启用，随时可访问；多模式中必须启用且仅启用一个。

多模式目前设计有三种：**构建模式、综述模式、深度研究模式**。

### 三种模式的职责

|模式|核心职责|Agent 角色|
|---|---|---|
|构建模式|检索、筛选、下载、解析论文，建立论文数据库底座|论文数据库构建者，线性工作流驱动|
|深度研究模式|基于已有论文库进行对话式深度探讨，支持 Graph-RAG 检索|研究助手，持续对话式驱动|
|综述模式|基于已有论文库自动撰写综述文章|综述撰写者，分阶段工作流驱动|

### 模式互斥设计理由

**三种模式运行逻辑截然不同，每种模式有自己独立的 Agent 链：**

- 构建模式的 Agent 链是**线性流水线**：按顺序执行七个阶段，每个阶段有明确的输入输出，阶段间有用户交互暂停点
- 深度研究模式的 Agent 链是**持续对话循环**：无固定终点，用户每次输入触发一轮 Graph-RAG 检索 + LLM 推理，结果实时流式返回
- 综述模式的 Agent 链是**多阶段审查工作流**：有固定阶段数，每个阶段需要用户确认才能推进，Agent 在各章节之间并行或顺序撰写

三条 Agent 链的状态管理、上下文结构、与用户的交互方式均不兼容，同时运行会造成状态混乱，因此设计为互斥模式。

### 模式切换规则

- 切换前若有运行中任务，弹窗询问用户：留在页面等待完成，或退出任务后切换
- 论文库（valid_papers）为 0 时，不允许切换到深度研究模式或综述模式
- 切换不影响各模式已有的历史数据（对话记录、综述草稿等均保留）

## 构建模式基础逻辑设计

Agent 链类型：**线性流水线**，用户可在每个非自动阶段后介入修改。

|阶段|执行类型|逻辑说明|
|---|---|---|
|检索词生成|LLM 调用|将用户课题描述输入 LLM，一次性生成搜索关键词，并针对 arXiv、OpenAlex、Semantic Scholar、Astrophysics Data System 生成多种高覆盖率的 Query 列表|
|检索与汇总|工具调用|顺序调用各数据库 API，将检索结果解析为统一格式（标题、作者、出版时间、期刊、摘要等），汇总到统一 List，基于 DOI / ArXiv ID / 小写标题去重|
|评分与筛选|LLM 调用|将 List 中所有文献的标题和摘要输入 LLM 进行评分（理论价值 0-5 + 技术价值 0-5），总分 > 7 认为有效，对比已有数据库去重，得到新增论文列表|
|下载与解析|工具调用|按新增论文列表逐一尝试下载 PDF 并解析为文本；下载失败时记录原因，以摘要作为该论文的文本信息|
|总结生成|LLM 调用|对每篇论文的文本信息调用 LLM，提取一句话总结、亮点解析、相关性要点、技术方法与创新|
|格式化与储存|工具调用|对关系型数据库和向量数据库进行增量写入（强一致事务）；同时触发图数据库的增量节点/边更新（最终一致）|
|邮件发送|工具调用（全自动）|提取数据库中未推送的有效论文，生成 HTML 格式邮件发送至配置的收件人；此阶段无用户交互暂停|

**阶段失败处理原则**：

- 工具调用失败（如网络超时）：自动重试最多 3 次，仍失败则记录错误并跳过该条目，继续后续处理
- LLM 调用失败：重试 1 次，仍失败则暂停当前阶段并通知用户
- 格式化与储存阶段：关系型数据库和向量数据库写入失败时立即整体回滚，不允许部分成功状态

## 综述模式基础逻辑设计

Agent 链类型：**分阶段审查工作流**，每个阶段完成后等待用户确认方可推进。

|阶段|执行类型|逻辑说明|
|---|---|---|
|扩写课题内容|LLM 调用|将用户课题描述输入 LLM，生成更完整的研究背景、研究范围和综述方向描述；用户审查并修改后确认|
|生成综述架构|LLM 调用|基于确认后的课题描述，LLM 设计综述的章节结构（标题、类型、各章要点）；用户可调整章节顺序、增删章节后确认；确认后生成 `review_outlines` 记录，版本号自增|
|撰写章节内容|LLM 调用 + 工具调用|按照确认的架构，逐章调用 LLM 撰写内容；撰写时通过向量检索从课题论文库中获取相关文段作为上下文，自动生成引用列表|
|自动审查迭代|LLM 调用|对每章内容调用 LLM 进行审查，检查准确性、引用规范性、逻辑结构；生成修改建议后用户选择是否接受；可多轮迭代|
|汇总成综述文章|工具调用|将所有已完成章节合并，自动生成摘要、关键词、参考文献列表；支持导出为 Markdown / PDF / Word 格式|

## 深度研究模式基础逻辑设计

Agent 链类型：**持续对话循环**，无固定终点，由用户的每一次输入驱动一轮推理。

**单轮对话执行流程**：

|步骤|执行类型|逻辑说明|
|---|---|---|
|接收用户输入|—|用户输入问题或观点，携带当前对话子模式（理论分析 / 技术讨论 / 实验设计）|
|Graph-RAG 检索|工具调用|以用户输入为查询，先做向量相似度检索，再在知识图谱中进行图扩展（多跳推理），合并结果后重排序，构建上下文；检索到的论文节点记录到本轮元数据|
|LLM 推理与生成|LLM 调用|将对话历史 + Graph-RAG 上下文 + 子模式 system prompt 一并送入 LLM，流式生成回复|
|写入对话记录|工具调用|将本轮用户输入、LLM 回复、引用论文列表、子模式状态作为一条轮次记录写入 `dialogue_turns` 表|

**子模式设计**：三种子模式共用同一条 Agent 链，区别在于注入不同的 system prompt，引导 LLM 的回复风格和关注重点：

- **理论分析**：聚焦概念解析、理论推导、框架对比
- **技术讨论**：聚焦实现细节、方案可行性、技术选型
- **实验设计**：聚焦实验目标、变量控制、评估指标

**只读约定**：深度研究模式的 Agent 链只读取论文库（关系型数据库 + 向量数据库 + 图数据库），不向任何数据库写入论文数据，不触发图谱重建。

## RAG 数据库设计

三种数据库均在构建模式的「格式化与储存」阶段写入，由构建模式统一维护。深度研究模式和综述模式只读，不负责建立或更新。

|组件|存储内容|用途|一致性策略|
|---|---|---|---|
|关系型数据库|DOI、标题、推送状态、抓取时间、AI分析等结构化元数据|流程管理（去重、定时推送、状态追踪）、元数据查询|强一致，写入失败立即回滚|
|向量数据库|论文全文/摘要的向量数据（分块存储）|语义检索、Graph-RAG 上下文构建|与关系型数据库强一致，同一事务写入，任意一方失败整体回滚|
|图数据库|论文、作者、关键词、概念、方法等实体节点及其关联边|知识图谱检索、多跳推理、Graph-RAG 图扩展、关系发现|最终一致；新论文入库时做局部增量更新，每日深夜后台全量重建|

**选型说明**：三个独立数据库而非单一方案，是因为三者查询模式根本不同——结构化过滤走 SQL、相似度检索走向量索引、多跳推理走图遍历——任何单一数据库都无法同时高效支持三种查询模式。
