## 2. 任务与审核流程

Codex执行原则与测试义务统一见[AGENTS](../AGENTS.md#codex-delivery-principles)及其验证要求；本节是工程阶段、业务决策和里程碑验收规则的唯一维护位置。任务模板和skill记录实例或引用本节，不另设逐任务人工审阅门禁。2026-10-25用户已授权本次流程调整；该授权不扩大任何业务任务范围。

项目级执行入口为 [project-delivery skill](../.agents/skills/project-delivery/SKILL.md)。调用示例：`使用 $project-delivery 推进已授权的任务队列`，或 `使用 $project-delivery 恢复任务X`。可先全量盘点需求并拆分任务、依赖、验收场景和覆盖缺项，分别标记已授权、待决策与延期；执行仍按已授权队列逐个可观察行为切片推进，不把全量拆解当作全量执行授权。

### 工程阶段（流程版本 v1.8）

| 阶段 | Codex交付及完成条件 | 人工职责 |
| --- | --- | --- |
| S1 范围与基线 | 明确授权队列、依赖、验收场景及所属里程碑；核对规范和实际文件，保存内容基线 | 既有批次授权可复用；仅处理未决范围或业务规则 |
| S2 实现与自验 | 从需求推导测试并完成最小实现、必需验证和自审；文档任务做文档核验 | 无例行审批 |
| S3 独立审查 | subagent自行阅读实际产物、规范与反例；缺陷修复、复验并复审闭合 | 新增业务决定按下节处理 |
| S4 覆盖性复核 | 重新逐需求检查成功、拒绝、失败及适用边界，补缺并验证；不能替代S2首次测试 | 仅裁决验收标准不明项 |
| S5 简化与维护性 | 检查重复、无用抽象与分支；保持业务行为、边界和断言强度；无收益记录无需修改 | 语义变化另行决定 |
| S6 最终复验与复审 | 对S3后实质变化执行受影响检查及独立复审；确认最终产物与证据一致 | 无逐任务补充接受 |
| S7 工程收口与交接 | 必需检查通过、独立问题闭合、覆盖无未解决必需缺项；保存最终基线、报告和状态，再核对下一项授权及依赖 | 达到里程碑时验收；工程收口不等于人工接受 |

### 授权、返工与恢复

- 队列记录任务ID、顺序、依赖、授权来源和限定范围。批量明确授权可复用，不逐项重问；待办登记、建单、设计批准或前任务验收不构成下一任务的实现授权。部署和外部通信不由本流程自动授权。
- 最新检查点置于任务单顶部（第8节），历史阶段记录留在原位置并链接：流程版本、阶段及状态、最近完成阶段、授权来源、产物快照与证据、业务待决项、里程碑状态及下一动作。每次交接、返工、等待或退出前更新。状态可为待开始、进行中、等待人工、阻塞、待核验、已完成或不适用（须依据）；S3独立审查不能标不适用或以自审代替。S5可完成并记录无需修改；S6复用未变产物的有效证据须说明依据。
- 恢复先核对原始授权/决定、快照和实际文件（含未提交/未跟踪文件），不能只信完成标签或HEAD。缺失证据回到最早受影响阶段；漂移保留旧证据，比较差异后重验/复审，不能直接刷新摘要继承结论。并行修改只暂停依赖部分，禁止回滚他人工作以匹配旧记录。
- 缺陷返回S2修复，执行受影响验证及独立复审，再检查S4–S6是否仍有效；无变化的有效证据可复用，不机械重跑。必需验证失败或未执行、独立审查不可用、范围内必需覆盖缺项未解决时，不得工程收口；保留具体阻塞、未验证范围和恢复步骤。真实外部依赖仍遵守隔离与授权要求。
- S3之后代码、契约、测试或规范发生实质变化，S6必须绑定新产物复验及按影响独立复审；单纯追加日志、状态或审查记录且不改变被审规则时可引用原结论，注明差异。无需为了记录审查本身无限复审。
- 旧流程v1.6及以前的S4是人工审查，S5是覆盖复核，S6是简化，S7是最终收口。恢复时保留原记录，追加新版本检查点：旧S1–S3按证据核对复用，旧S5→新S4，旧S6→新S5，旧S7证据按新S6/S7条件分别核验；旧S4决定归入业务决定或历史接受记录，不映射为新S4完成。仅等待例行人工审阅的任务可在原授权内继续工程阶段；真正未决业务规则或明确里程碑门槛仍保留。不得批量改写历史待审状态或倒填执行证据。

### 上下文、证据与增量审查

2026-10-28用户授权以下工程优化，并确认“审查改动及受影响依赖，未改动且证据仍有效的部分复用原结论”。S1–S7顺序、逐需求测试义务、独立审查及D/M边界不变；v1.7恢复无需重做已有效完成的阶段。

- 入口先读当前状态、任务顶部检查点和相关规范段落。相同内容已读且基线未变时复用上下文；历史仅在追溯授权、证据缺失或冲突时展开。首次审查或没有可信基线时，建立本任务范围的完整基线，不以“无diff”推定通过。
- 每次审查记录上次有效审查基线→当前产物的差异，含相关未提交、未跟踪和删除文件。Git commit可定位已接受基线，但不能取代实际工作区快照或证明审查通过。复审重点为差异及受影响调用链、契约、权限、持久化、测试与规范；未改动文件若受到影响仍须审查。审查者可沿依赖扩展，不能只看diff行或主agent摘要。
- 委派默认提供有界任务包：授权、规范位置、基线/差异、产物路径、验证入口及允许副作用、未解决问题。避免复制全部会话；审查者独立读实际文件和反例，输出发现、依据、验证限制与覆盖范围。复杂跨边界变更可拆分审查职责，避免多人重复全审。
- 第4节需求矩阵与第5节验证记录各维护一份；阶段表、状态入口和交付报告引用证据，不重复展开日志。S4仍逐需求检查本任务及受影响既有需求，不能仅核对新增测试。S5无收益则记录无需修改。
- S2先检查声明的运行时、测试隔离和迁移等适用前置，再做专项验证；必需完整验证仍须完成。S6按差异与影响复验/复审，注明复用证据的产物、环境和有效性；无法证明影响范围或证据失效时扩大检查。所有必需用例仍须有有效通过证据，不减少断言或适用边界。
- 完整日志、快照和清单留在文件中，工具默认返回摘要、失败位置和证据路径，必要时定向展开。快照使用现有delivery_snapshot.py等机械核验入口，不把大量哈希反复输入模型。已完成进程不重复轮询。

### 人工接受后的Git提交

2026-10-28用户授权：今后每次阶段里程碑获得实际人工接受，完成对应工程收口与基线核对后自主创建本地Git commit，无需再次请求提交批准。该规则不把S1–S7每阶段变成人工门禁，不自动追补历史里程碑，不授权push、部署或重写提交历史。

1. 记录人工接受原话/来源、日期、里程碑ID、范围和接受快照。先核对接受后差异；行为、契约、验收标准或关键边界变化按补充验收规则处理。纯接受记录等变化注明依据。
2. 提交范围限定为该里程碑已接受的产物及必要记录。检查已有暂存区，按明确文件/补丁暂存并检查staged diff；不得直接git add -A夹带进行中任务、无关修改、凭据或本地运行产物。已有未提交的前置交付必须核对归属和有效接受，必要时明确纳入提交清单，不能默认为本次新获接受。
3. 同文件混有后续未验收变更时，使用精确补丁或隔离索引构造已接受内容，并验证提交树与接受基线一致；保留工作区和他人暂存内容。不能可靠分离、缺少前置或发生漂移时仅暂停提交，记录原因，继续独立已授权工作，不为了提交回滚现有文件。
4. 提交信息包含里程碑ID和可观察成果。提交后核对commit内容与范围、剩余工作区及暂存区；在任务检查点记录commit SHA、接受基线与未提交范围。该SHA记录在后续检查点保存，不为写入自身SHA循环提交或amend。commit不替代验证或人工接受；重复恢复先核对已有提交，避免重复/空提交。

### 业务决策与里程碑验收

- **业务决策D**可在任意阶段触发：业务语义、权限边界、人工内容保护、知识版本绑定或产品分期的未授权变化，以及范围扩大、旧数据接入/迁移、生产保留政策等未决事项。提交问题、证据、选项及影响、建议和仅被阻塞的工作。按现行已定规则实现或修复不需再次审批；决定到达后恢复受阻阶段，不跳过工程验证。
- **里程碑验收M**针对可使用的业务成果或用户明确指定的验收点，不默认每个小任务都是里程碑。S1记录所属里程碑ID、范围、验收场景、触发点和依赖它的后续工作；可复用现有约定。若尚无约定，先提出业务成果分组，在首个完整业务成果形成时提交验收；不得因未命名里程碑无限推迟验收。纯流程/文档任务没有独立业务成果且用户未要求人工验收时，记录“不单设里程碑”及理由。
- 到达里程碑后，先完成相关工程阶段，再提交单一验收包：最终产物基线、任务范围与需求追踪、可复现演示/场景、自动验证和独立审查证据、未验证项及风险。状态记“工程已收口；里程碑待验收”。人工可接受、要求修复或提出新增需求；缺陷在原范围内修复复验，新增需求另行授权。等待期间继续不依赖该验收的已授权任务，不跨越明确验收前置。
- 没有实际答复时，D/M保持等待人工；沉默、超时、subagent建议或自动测试通过均不代表批准。记录真实用户消息/审核记录、日期、范围与基线。人工节点不反复轮询，保存可恢复交接。
- 里程碑接受后若相关行为、契约、验收标准或关键边界变化，完成工程复验/复审并提交受影响范围的补充验收；旧接受只对原基线有效。纯记录追加或经复验确认不影响已接受范围的维护改动，记录差异与依据即可，不恢复逐任务人工门禁。
- 工程收口、业务决定和里程碑接受分别记录；所有任务工程完成不能自动关闭尚待人工验收的里程碑，也不能声称产品已整体接受。

[Project创建幂等示例](../tasks/004-project-create-idempotency-example.md)仅演示填写，不授权编码，也不关闭A04/A10；旧示例的人工审核字段按上述恢复规则理解。

### 里程碑人工验收要点

以里程碑涉及的现行规范为准，逐项选择适用检查；下表只提供审核视角，不新增业务语义。

| 审核对象 | 要回答的问题 | 可检查的证据 |
| --- | --- | --- |
| 需求与用户行为 | 成功、拒绝和失败是否符合预期；每个可测需求是否有面向需求的用例且通过 | 需求追踪表、演示、断言与当前运行结果；缺项不能用通过率掩盖 |
| Project隔离与权限 | 身份共享是否泄露其他Project文件或分析；读取、下载和结果提交是否执行适用授权 | 授权位置、跨Project负例、撤权场景及持久副作用 |
| 状态与写入所有权 | Workspace恢复是否越界写业务状态；知识版本是否仅由成功Construction Run发布 | 应用写入入口、事务边界、失败及迟到Worker测试 |
| 版本与人工保护 | 旧Session/Review是否保持绑定；Agent是否覆盖人工确认或编辑内容 | 版本选择与提交条件、旧版本读取及并发编辑反例 |
| 持久一致性 | 重复、并发、响应丢失或提交失败是否导致重复与部分写入 | 唯一约束、事务代码、真实存储与确定交错的测试 |
| 证据可信度 | 检查是否针对当前产物；反例能否识别错误实现；隔离和清理是否成立 | diff、基线、实际命令、报告与残留记录；mock和静态检查不得冒充端到端验收 |

不要求平均阅读每行代码，应直接检查权限、事务、绑定和提交资格等关键位置，并对重要场景亲自复现或抽查。不能仅依据Codex总结或测试数量接受交付。审核结论记录审核者、日期、产物基线、接受范围及问题处置；未验证项保留明确状态。“看起来不错”不能替代有范围的接受记录，自动检查通过也不代替人工结论。
