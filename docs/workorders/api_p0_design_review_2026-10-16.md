## 1. 授权与基线

用户授权按前述建议补齐 API，优先 P0，同步应用设计和项目状态，保持现有业务边界与分期；要求 API、附录拆分、限制说明先由 subagent 独立思考、设计和审计，再由主代理评审调整后修改。

本轮读取项目状态、设计索引、01 需求、02 及领域附录、03 UI、04/05/08/09 草案和 Git 工作树。已有未提交修改属于当前工作基础，本轮不还原。新核心未实现，旧片段不作为 API 可用或验收证据。工作期间另有并行修改把 02-02 升为 v1.3 并加入第 10 章“未生效状态机评审提案”；该变更不属于本轮，保持原样，API 仍只承接其第 1–9 章现行规则，不采纳候选状态或转换。规范入口见 [04](../design/04_api_contracts.md)和 [05](../design/05_application_use_cases.md)。

独立设计工作分别研究 P0 操作、传输/任务/文件协议及业务边界。边界审计首先建议按账号配置、构建知识、研究综述、异步传输拆分四份附录；主代理评审认为维护面过大，改为更小结构：

| --- | --- |
| 04 主文 | 公共响应、修订、幂等、权限/分期和路引；不重复领域规则 |
| [04-01 P0 操作](../design/04-01_p0_operation_contracts.md) | FR—用例—操作映射及请求响应字段、前置条件、失败与确认 |
| [04-02 传输任务文件](../design/04-02_transport_task_file_contracts.md) | TaskHandle、SSE、取消/回放、上传及授权下载 |

| 本记录 | 独立预案、评审取舍、真正业务待决和文档验证证据 |

主代理采纳：P0 字段与失败契约优先，技术参数可设明确默认/上限，不因认证方式、分页、修订号、任务地址等技术选择请求业务裁决；OpenAPI 全量机械转写不在本轮编写，不据此声称已完成可执行 schema 验证。新增规范不能把 06/07/10、SQL 或候选 Graph-RAG 方案整体升级为定稿。

独立审计要求保留的限制：Construction 唯一发布者；候选/正式知识隔离；每个 Session/Review 固定单一版本；采用新版本创建独立对象；迟到结果与旧确认不覆盖人工修改；Project 私有文件不因 PaperIdentity 共用而外泄；管理员诊断不授予 Project 内容权限。通用恢复/自动调度/邮件/导出保持 P1，协作和 Review 完整历史保持 P2。

特别修正：重新评分、章节重新生成/审查属于对应 P0 FR，不等于 P1 通用失败恢复；基础 Research 引用跳转属于 FR-028 P0；可导出版本形成属于 FR-034 P0，文件导出中心仍为 FR-019 P1。Review 默认接受不增加人工确认门槛，也不冒充人工确认。

## 3. 需人工决定的局部业务问题

历史预案：本节及第 5–6 节保留提出时的选项与证据。用户现已采纳 D01 A、D02 B、D03 A、D04 A、D05 A、D06 A、D07 A；当前生效结论和剩余细则统一见第 7 节，旧“未批准/待决”措辞仅描述当时状态。

### API-D01：返回检索与冻结输入

- 问题：FR-022 明确允许返回检索阶段补充检索词；02-02 §3 冻结本轮输入并规定配置修改默认下轮生效，但只明确本轮候选修正，没有定义返回检索如何改变冻结输入。
- 证据：[FR-022](../design/01_functional_requirements.md#fr-022-论文与资料去重评分与筛选)、[02-02 §3](../design/02-02_construction_versioning_appendix.md#3-构建默认行为)。
- 选项 A：同 Run 保存显式输入修订，失效受影响检索/筛选/确认并重做；保持原始冻结快照可追溯。选项 B：结束当前构建，另建 Run 并明确新基线；改变了“返回本轮”的使用方式。
- 推荐：A 更贴合已有 FR，但需明确是否允许修订原始运行输入及其恢复语义。
- 阻塞：仅“返回检索补充词”命令的状态转换、输入快照与失效规则；普通新构建、候选编辑和重新评分继续定约。

### API-D02：Research 消息变更与片段采纳分期

- 问题：02 §7 和 02-04 §5 定义单条消息编辑/删除、失败片段编辑/采纳；FR-028 为 P0，FR-030 为 P1，未明确这些操作归属。
- 证据：[02 §7](../design/02_domain_core.md#7-research-session-领域规则)、[02-04 §5](../design/02-04_run_recovery_appendix.md#5-research-回复恢复)、01 FR-028/030。
- 选项 A：将上述消息级操作明确纳入 P0，补齐保护及引用保留验收。选项 B：作为 P1 增强，P0 只保证输入/失败片段/诊断可追溯、取消及继续新轮次。
- 推荐：B 较小且不影响既有 P0 对话闭环；但分期由人决定，不能把领域已写规则删除或宣称已实现。
- 阻塞：仅消息级变更与片段采纳是否进入 P0；成功回复和失败记录持久化、引用读取与取消不受阻塞。

### API-D03：严格引用覆盖判定

- 问题：FR-033 已明确默认提示、严格模式阻断，但未定义何为“引用不足”的可验收标准；接口不能自行发明覆盖百分比或逐段引用政策。
- 证据：01 FR-033、[02 §8](../design/02_domain_core.md#8-review-run-领域规则)。
- 选项 A：明确基于结构规则/阈值的可解释判定。选项 B：基于 Agent 审查结论判定并定义置信与人工处理边界。
- 推荐：优先 A 的可复现规则，并明确引用定位失效等基础失败；具体指标须另行批准。
- 阻塞：严格覆盖判定算法及其数值/规则验收；策略字段、结果/问题显示、默认提示及明确不通过时拒绝确认可定约。

### API-D04：活跃任务下 Project 操作的终结呈现

- 问题：归档/删除/清理的安全写入边界已有约束，但并发活跃任务最终显示为何种状态、何时结束以及清理故障呈现未完整定义。
- 证据：[02-02 验收 A16](../design/02-02_construction_versioning_appendix.md#8-可验证验收场景)已要求后续写入拒绝或安全终止；01 FR-008 定义归档只读、删除不可进入及清理范围。
- 选项 A：命令提交状态后使执行资格失效，异步安全终止并显示各任务结果。选项 B：先要求显式取消活跃任务再执行 Project 操作，增加操作前置条件。
- 推荐：A 符合现有“拒绝后续写入或安全终止”约束；需确定任务终结/清理结果呈现，不能擅自增加 B 卡口。
- 阻塞：仅状态终结与部分失败呈现的局部定义；已定状态检查、迟到写入拒绝、共享引用保护及非活跃操作不阻塞。

### API-D05：ReviewRun 完成判据与成功后编辑

- 问题：FR-034 允许终稿编辑/摘要参考文献重新生成，且终稿默认 accepted；02 §3.2 又规定 succeeded 历史实例不得原地 running。缺少终稿接受与 ReviewRun 整体完成的明确关系。
- 证据：01 FR-034/035、[02 §3.2](../design/02_domain_core.md#32-通用状态)、[02 §8](../design/02_domain_core.md#8-review-run-领域规则)。
- 选项 A：终稿 accepted 仅为内容状态，Review 容器继续可编辑，另行定义 Run 完成条件。选项 B：accepted 即完成 Run，之后编辑/生成走独立新结果或新 Run，并定义最小追溯关系。
- 推荐：A 更贴合主流程连续编辑，但完成判据需明确，不能在 API 中新增未授权的“关闭综述”能力。B 也不能借 P2 历史功能作为 P0 前置。
- 阻塞：仅 ReviewRun 进入 succeeded 的判据及该状态之后编辑/生成路径；大纲/章节/终稿任务契约与默认接受/显式拒绝不受阻塞。不得把 final accepted 自动映射 Run succeeded，也不得原地复活已 succeeded 实例。

## 5. 评审补充：终稿编辑与其他局部限制

### API-D06：人工编辑终稿后的可导出快照生命周期

- 问题：FR-034 明确可编辑终稿，并要求导出内容与可导出版本一致；尚未明确人工编辑后，是立即产生新的 accepted 快照，还是使当前稿对应的可导出结果过期并重新生成。
- 证据：01 FR-034 的编辑范围、已过期需重新生成状态、生成失败不得覆盖既有 accepted 版本；02 §8 的独立结果和旧 accepted 保留规则。
- 选项 A：编辑保存新的当前内容修订，原 accepted 快照保持不可变；新稿的可导出状态变为过期，显式重新生成后形成新 accepted 结果。选项 B：保存编辑同步构建新的 accepted 可导出快照，并定义参考文献/终审更新要求。
- 推荐：A 便于确保终审与引用一致性；但是否需要再次生成属于用户流程决定，不自行新增门槛。
- 阻塞：仅人工编辑之后新稿与可导出快照的状态关联及生成触发语义；不可原地覆盖旧 accepted 快照，普通首次生成/拒绝协议继续完成。

其他限制分类：密码重置响应丢失按技术协议同键不再次重置且不重放密码，用户显式新键才产生新密码，不列为业务待决。运行期凭据获取、失败临时产物清理期限属于后续工程参数，不阻塞 API 整体。管理员删除用户时历史已完成导出结果的处置属于 P1 文件生命周期，若后续发现空白应单列，不阻塞无导出资产的 P0 删除路径。

## 6. API 边界收敛（2026-10-16，本次）

用户授权先修改不涉及业务决策的部分，逐项列出业务选项并同步状态。本节为本次增量记录，第 1–5 节的验证数字与并行状态描述属于此前任务快照，不作为本次重新验证结果。未采纳任何业务推荐，不修改需求、领域状态、权限或产品分期。

已修改 04、04-01、04-02、05：

- 保留既有阶段、人工覆盖、治理、清理、无证据继续及版本采用确认要求；只限定哪些详情负责提供凭据，普通详情不再必须计算全部确认预览。
- 纯预览不要求 Idempotency-Key，不重放旧 token，不创建业务任务/修改修订；真正有副作用的 POST 仍要求幂等。现有 GET 预览继续只读。
- API 维护 202 可靠受理、迟到结果保护及快照一致性等可观察保证；去重竞争、事务和派发顺序集中到 05。
- 移除只返回 blocked 的返回检索占位路由；API-D01 保留待决，在现有动作可用性中提示原因，不引入通用命令入口。
- 明列补充/候选文件身份、file-access 和下载路由，承接已有 Project 读取权限与候选隔离，不新增权限、保留期限、文件执行或正式引用资格。

### API-D07：纯补充、纯修订的发布入口

- 问题：清空关联、分析修订等已形成待发布修订，但 ConstructionStart 只定义非空检索词的常规检索构建；是否允许无需新检索的发布路径？
- 证据：[04-01 第 4 节](../design/04-01_p0_operation_contracts.md#4-construction-配置补充请求与候选处理)中的 ConstructionStart、pending-revisions、association-clear-confirm；[02-02 第 2 节](../design/02-02_construction_versioning_appendix.md)要求范围变更通过 Construction 发布。
- 选项 A（推荐）：允许同一 Construction 边界内的补充/修订模式，必须有非空已确认补充或明确修订输入；省略新检索但仍检查当前基线、独占写资格、相关人工确认和完整发布条件。需定义排除全部资产时的空知识版本语义，不能默认绕过现有有效结果门槛。
- 选项 B：P0 仅随下一次常规检索构建纳入；界面清楚标为未发布。实现较少，但单纯修正/排除也要进行检索，无法独立完成。
- 推荐理由：A 能形成修订闭环且不破坏唯一写者边界；新增运行入口及空结果规则需人工批准，不能仅通过允许空 selected_terms 实现。
- 阻塞：纯补充/纯修订专用启动字段、跳过阶段规则与验收；常规检索构建及待纳入修订保存继续按已定协议执行。

### API-E01：严格引用的可执行判定标准

证据：FR-033 规定默认提示、严格阻断；D03 A 已选择结构规则。结构覆盖可以稳定验证，但不能证明文献在语义上支持论断。

- **A（推荐）：以内容块为单位，要求 100% 覆盖。** Markdown 的正文段落、列表项和表格数据行为单位；标题、目录、参考文献列表、纯格式节点不进入分母。其他块默认需要引用；过渡语、作者自行提出的研究设想等只能由用户逐块标记豁免并填写原因，Agent 可建议但不能自动豁免。表格标题/表注只有显式关联到指定行才计覆盖，不能凭相邻位置猜测。引文必须属于同 Project、同绑定版本、当前可访问，且定位可解析；裸 DOI、未定位引用、仅列在文末的参考文献不算块覆盖。合格块数/非豁免块数须为 100%，所有显式引用都须有效；分母为零返回 unknown，不能按 100% 自动通过。结果保存规则版本、章节修订、覆盖/豁免/缺失块与原因；结构不明确或无法验证返回 unknown，strict 下拒绝确认。相同规则、修订和证据可用性快照得到相同结果，确认前再验证当前权限与定位。Agent 的论据充分性建议继续显示，不参与结构通过裁决。
- B：同样的块与证据定义，阈值为 90%，仍要求所有显式引用有效。改动负担较低，但严格模式可能容许未引用的正文；需明确接受这一含义。
- 推荐理由：A 可复现、失败可定位，没有隐含模型评分。代价是需要更多逐块引用/豁免操作；它是结构覆盖标准，UI 必须避免称为“科学正确性验证”。
- 阻塞：strict 判定器与通过验收；默认风险提示、规则版本投影、引用跳转及 strict unknown 阻断可继续。
