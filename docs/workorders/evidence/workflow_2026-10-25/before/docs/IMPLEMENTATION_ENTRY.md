## 2. 任务与审核流程

Codex执行原则与测试义务统一见[AGENTS](../AGENTS.md#codex-delivery-principles)及其验证要求；本节维护人工审核与双方交接流程，任务模板只记录本次实例。人工决定产品取舍与最终接受，Codex负责交付质量和验证证据。

项目级执行入口为 [project-delivery skill](../.agents/skills/project-delivery/SKILL.md)。调用示例：`使用 $project-delivery 推进已授权的任务队列`，或 `使用 $project-delivery 恢复任务X`。调用不增加授权范围；下列阶段用于该流程，新任务采用，旧任务恢复时保留历史并补充检查点，不倒填未执行阶段。

| 阶段 | Codex交付及完成条件 | 人工职责 |
| --- | --- | --- |
| S1 范围与基线 | 明确授权队列、依赖与验收场景，核对规范和实际文件，保存内容基线 | 明确范围；裁决业务冲突 |
| S2 实现与自验 | 最小实现、需求追踪与必需验证通过，自审完成；文档任务做文档核验 | 按需澄清，不代替基础调试 |
| S3 独立审查 | subagent 阅读实际产物与规范；发现的缺陷修复、复验并复审闭合；缺工具则保持未执行 | 新增范围另行决定 |
| S4 人工审查与决策 | 提供单一审核包及精确基线；明确接受所需范围才进入S5；要求修复回S2；仅业务裁决则恢复原阻塞阶段 | 接受、要求修复或裁决，记录来源、范围、基线 |
| S5 覆盖性复核 | 按需求重新检查成功、拒绝、失败及适用边界；补缺并运行验证 | 仅裁决标准不明项 |
| S6 简化与维护性 | 检查重复、无用抽象与分支；保持业务行为、边界和断言强度；可记录无需修改 | 语义变化另行决定 |
| S7 最终复验与收口 | 复验受影响检查、复审后续实质改动，确认最终基线的人工接受仍有效；同步证据和项目状态 | 对审核后产物变化补充接受 |

### 授权、返工与恢复

- 队列必须记录任务ID、顺序、依赖、授权来源和限定范围。批量明确授权可复用，不逐项重问；待办登记、建单、设计批准或前任务验收不构成下一任务的实现授权。部署和外部通信不由本流程自动授权。
- 检查点保存在任务单第8节：当前阶段及状态、最近完成阶段、授权来源、产物快照与证据、待决问题、下一动作。每次阶段交接、返工、等待或退出前更新。每个阶段状态为待开始、进行中、等待人工、阻塞、待核验、已完成或不适用（须依据）；不得将S3独立审查或S4人工审核标为不适用来跳过。
- 恢复先核对原始授权/决定、快照和实际文件，不能只信“已完成”标签或HEAD。缺失证据则标待核验并回到最早受影响阶段；内容漂移保留旧证据，比较差异后重验/复审，不直接刷新摘要继承批准。并行修改只暂停依赖部分，禁止为匹配旧记录回滚他人工作。
- 缺陷返回S2修复，再执行受影响验证和S3复审；业务歧义返回S4决策（可在任意阶段提出），决定到达后恢复被阻塞阶段，不跳过尚未执行的S2/S3。新增需求另列授权。必需验证失败或未执行不得记为通过；真实外部依赖仍遵守AGENTS的隔离与授权要求。
- 人工节点无实际答复时保存“等待人工”，交接后等待用户；沉默、超时、subagent建议或自动测试通过均不代表批准。引用真实用户消息/审核记录及日期，可以忠实转录，不伪造审核者。常规工程选择和已授权修复不重复索取批准。
- S4之后若交付内容改变，S7必须比较审核基线：代码、契约、测试或规范变化均须复验、按影响独立复审，并将变更后的具体产物回交S4补充接受；不能把旧接受迁移到新摘要。只有追加执行日志、状态或审核记录且未改变被审产物/规则时，可引用原接受，注明差异。不要求因记录接受本身再次审核。再次接受后，无新变化的S5/S6证据可复用，避免无限循环。
- 只有所有必需检查通过、独立问题闭合且最终产物人工接受有据，才记为任务收口；否则交付工程结果并明确待审核/阻塞。继续下一项前重新核对其已有授权和依赖。等待期间可做已授权独立准备工作，但不据此宣布当前门槛通过或启动未授权业务任务。

[Project创建幂等示例](../tasks/004-project-create-idempotency-example.md)仅演示填写，不授权编码，也不关闭A04/A10。

### 人工审核要点

以任务涉及的现行规范为准，逐项选择适用检查；下表只提供审核视角，不新增业务语义。

| 审核对象 | 要回答的问题 | 可检查的证据 |
| --- | --- | --- |
| 需求与用户行为 | 成功、拒绝和失败是否符合预期；每个可测需求是否有面向需求的用例且通过 | 需求追踪表、演示、断言与当前运行结果；缺项不能用通过率掩盖 |
| Project隔离与权限 | 身份共享是否泄露其他Project文件或分析；读取、下载和结果提交是否执行适用授权 | 授权位置、跨Project负例、撤权场景及持久副作用 |
| 状态与写入所有权 | Workspace恢复是否越界写业务状态；知识版本是否仅由成功Construction Run发布 | 应用写入入口、事务边界、失败及迟到Worker测试 |
| 版本与人工保护 | 旧Session/Review是否保持绑定；Agent是否覆盖人工确认或编辑内容 | 版本选择与提交条件、旧版本读取及并发编辑反例 |
| 持久一致性 | 重复、并发、响应丢失或提交失败是否导致重复与部分写入 | 唯一约束、事务代码、真实存储与确定交错的测试 |
| 证据可信度 | 检查是否针对当前产物；反例能否识别错误实现；隔离和清理是否成立 | diff、基线、实际命令、报告与残留记录；mock和静态检查不得冒充端到端验收 |

不要求平均阅读每行代码，应直接检查权限、事务、绑定和提交资格等关键位置，并对重要场景亲自复现或抽查。不能仅依据Codex总结或测试数量接受交付。审核结论记录审核者、日期、产物基线、接受范围及问题处置；未验证项保留明确状态。“看起来不错”不能替代有范围的接受记录，自动检查通过也不代替人工结论。
