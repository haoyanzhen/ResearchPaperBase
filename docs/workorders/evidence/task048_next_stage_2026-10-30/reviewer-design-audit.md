## 结论

1. 允许手动确认有效分析的成功子集进入候选入库，不要求全部分析成功作为全局新门槛。依据：FR-025（1148–1182）明确失败/部分失败可重试或人工补全，手动分析确认后进入入库；02-03 §6（119–134）只允许确认后的 PaperAnalysis 进入候选入库；02-02 §2.3（61–74）要求手动入库预览同时显示有效项与失败/跳过项；FR-026（1183–1243）要求版本含本次成功参与构建项。成功子集必须在明确显示失败范围与后果的确认中选定，不能把失败当成功。失败项保留诊断与补全/重试，不获得有效 analysis/basis，不作为写入集合；本轮未纳入不能自动转换为持续的人工排除，不更改既有版本成员。

2. 全文容量不足已有合法失败路径，不必先发明切分/融合/截断策略。04-04 §2（13–24）规定冻结声明容量、预留输入/输出/协议开销以及 Provider 超限明确失败；FR-025允许失败后的重试/人工补全；06 A08.3（246–253）只使用已确认 PreparedTextRef，不允许无依据伪空成功。可整篇调用，明确失败；不静默替换为摘要，也不将被截断输出当完整分析。

3. 未设置输出上限时，04-04 §6（47–49）已明确其他调用继续 Provider 缺省，4096仅 llm_text_cleanup。因此“分析自动加4096”与“未填就拒绝分析”均是新增语义，若要采用必须人类决定；保留 Provider 缺省本身已有依据，不需再次审批。需诚实区分声明容量/估算预留与最大总容量保证：缺省输出未知不能声称精确预检保证，Provider 超限仍失败。若实现打算要求派发前确定最大总容量，则新增要求与既有 Provider 缺省有张力，应提决策；不能只因 cleanup_capacity API 要求确定 max 而把实现复用便利变成业务门槛。

4. task047 D-PDF-04（126–140）确曾对整理引擎输出预留提交人类选择；现行规范把结果明确限于整理。该先例不授权扩展4096，也不能替代当前范围判断。建议主代理明确选择保留既有 Provider 缺省且不承诺严格预检，或向用户提出具体新增默认/必填要求；不要将长文分块当完成 FR025 的强制前置。
