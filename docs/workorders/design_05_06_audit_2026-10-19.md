## 1. 范围与结论

审计当前工作树的 05 v1.11、05-01 v1.0、06 v1.8，对照 01 需求、02 领域及专题附录、03 相关交互、04 及操作/传输附录，并检查 00 依赖方向。开始时工作树已有设计修改及未跟踪的契约、脚本和工作单；这些变更作为被审基线保留。本次不是仅检查 Git 新增行，旧段落遗留问题也计入，但明确区分来源。

结论：05/05-01 的总体架构合理，本轮未发现它们改变核心业务裁决的明确证据。06 尚不能作为完整服务实施规格：发现一处确认语义歧义、一处新增契约覆盖缺口、两处既有服务细化问题和一处分期表述问题。以下 P2/P3 为审计严重度，不是产品阶段 P0/P1/P2。没有发现需要推翻现有架构的阻断性问题；不等于所有实现边界已闭合。

## 2. 发现

### A01（P2）：大纲编辑被写成确认的替代条件

- 位置：[06 §6](../design/06_agent_knowledge_services.md#6-review-pipeline)，当前第 103 行：“大纲生成后必须经过用户确认或编辑”。此句为既有段落。
- 依据：[01 FR-032](../design/01_functional_requirements.md)、[02 §8.1](../design/02_domain_core.md)、[04-01 §7.2](../design/04-01_p0_operation_contracts.md#72-操作)均要求确认大纲后才能生成章节；05 §9 更明确“编辑不等于确认”。03-03 P26 也分别呈现编辑与确认。
- 影响：按 06 的“或”实现流程，可能在只保存编辑后开放章节生成，跳过绑定当前修订和知识版本的确认。上游规则足以裁决，不能将其解释为新业务选择。
- 建议：改成允许编辑，但章节生成必须另有当前大纲修订的有效确认；编辑使相关旧确认失效。
- 后续验证：保存编辑而未确认时生成章节被拒绝；确认后再编辑，旧确认不能用于生成。

### A02（P2）：新增外部产物写入契约没有覆盖 Run 之前的补充文件

- 位置：[06 §3.3](../design/06_agent_knowledge_services.md#33-结果提案与端口实现)第 72 行，将准备外部文件统一限定在“所属隔离候选空间”；[05-01 §3.2](../design/05-01_internal_module_contracts.md#32-执行与知识上下文)的 CandidateWriteScope 必须包含 ConstructionRun、attempt 和候选修订。
- 依据：[04-02 §4](../design/04-02_transport_task_file_contracts.md#4-单文件上传与补充处理)允许先上传并异步解析独立 supplement；同文 §5.1 明确 supplement 文件的 run_id=null，candidate 文件才必须有 Run。05 §7 也允许独立待纳入请求。
- 影响：若把 CandidateWriteScope 用作所有文件准备的唯一资格，首次上传或构建期间的下轮补充将无合法写入上下文；伪造 Run 或借用当前 Run 又违反冻结输入边界。这是新增工程契约的覆盖缺口，不是上游上传需求冲突。
- 建议：区分补充请求暂存范围与 Run 候选范围，明确归属、资格、纳入时关联及清理责任；不得将暂存文件视为正式证据。可采用独立类型或具名联合，不强制具体类型名称。
- 后续验证：没有 Run 时可以上传；存在 Run 时补充仍独立待纳入；取消旧 Run 不误清理独立补充。

### A03（P2）：统一输出校验混用了候选与已发布证据边界

- 位置：[06 §8](../design/06_agent_knowledge_services.md#8-输出校验)第 117 行，要求“所有 LLM 结构化输出”校验引用论文属于绑定 Knowledge Version。此句为既有段落。
- 依据：[02-03 §6](../design/02-03_construction_assets_appendix.md#6-文本处理与分析确认)规定论文/资料先分析、确认，再候选入库；[02-02 §2.3](../design/02-02_construction_versioning_appendix.md#23-资产纳入与图谱边界)规定发布后才能作为正式研究证据。05-01 已区分 ReadContext 与 CandidateWriteScope。
- 影响：若统一校验器把构建分析的候选来源引用当作正式 EvidenceRef，首次构建没有已发布版本、新候选不在基线内，合法分析会被拒绝。反过来放宽正式 EvidenceRef 又会泄漏未发布知识。当前文本没有声明适用分支，不能据此断言实现已经存在该缺陷。
- 建议：通用 schema 校验之外按操作区分：候选分析校验候选归属、修订及已确认处理文本；Research/Review 的正式证据校验绑定版本成员；检索词建议等无证据输出不强造版本。证据类型同时覆盖 paper/material。
- 后续验证：首次构建候选分析成功、跨候选引用拒绝、Research 读取未发布候选拒绝、合法 material 证据通过。

### A04（P2）：非论文资料链路仍未完整展开

- 位置：06 §4 第 80–82 行只展开论文身份去重、PDF/摘要降级和论文严格分析；§7 第 111 行解析端口仅列 PdfParser；§5 第 96–97 行证据包和跳转也只描述论文。均为既有段落。
- 依据：[02-03 §5–6](../design/02-03_construction_assets_appendix.md#5-手动补充与资产边界)要求 P0 多种资料格式、标题与格式组去重及轻量 MaterialAnalysis；04-01 第 140 行区分 PaperAnalysis/MaterialAnalysis，第 204 行 EvidenceRef.asset_kind=paper|material；01 FR-028/033 和 03 的引用面板均包含资料。
- 影响：仅按这些服务段落实施，会遗漏非 PDF 资料解析，或对资料错误要求论文分析字段，并丢失资料引用入口。06 的草案声明使其属于已知完整性缺口，不代表新增裁决取消了资料能力。
- 建议：在服务细化时明确 paper/material 分支、格式能力端口、处理状态、轻量分析结果和统一资产证据；具体解析库不必在此选定。沿用 TRACK-008a，不另起重复实现事项。
- 后续验证：至少覆盖一种非 PDF 的 P0 资料，从接收、解析、轻量分析到发布后引用解析的完整路径。

### A05（P3）：Research 输出倾向缺少 P1 限定

- 位置：06 §5 第 95 行将创新/实验/总结写成每轮提示策略，未标明分期；为既有段落。
- 依据：01 FR-029 明确 P1，04-01 §9 同样保留输出倾向为 P1。05 §2 的分期摘要没有列出这一项。
- 建议：补 P1 标记及未启用时不影响 P0 普通回复的说明。此处是分期歧义，不能据其断言已提前实现或正式改变分期。

## 3. 合理且与上游一致的部分

- Workspace 只保存操作现场，业务内容由 Construction/Research/Review 所属应用模块提交。
- Agent 返回提案，应用重新校验当前授权、修订、确认及执行资格；取消与成功提交排他，不依赖 Provider 是否及时停止。
- ReadBinding 可持久化，ReadContext 的读取保护重新取得；不把版本绑定或句柄当永久授权，不回退 latest。
- 隔离产物准备与最终发布分开；published/no_change、空版本、暂停占槽和旧研究固定绑定均承接领域规则。
- 内部事件为持久事实，公开 SSE 仍由 04 定义；不强制事件溯源、分布式事务或独立微服务。

上述边界适合当前模块化应用。无需为解决本轮问题增加新架构层；先补齐已有类型和条件分支即可。
