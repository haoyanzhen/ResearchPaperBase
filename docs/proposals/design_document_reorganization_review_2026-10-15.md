## 1 范围与方法

审查者读取提案、AGENTS.md，对照现行需求、领域、UI、API、应用用例、知识服务、数据及 SQL、安全、质量、运维和历史审查文档，重点核实：

- 是否保留六层架构、FR 编号、需求与分期。
- 文件调整依据是否成立。
- 结构变更、语义对齐、待裁决事项是否明确区分。
- 附录迁移是否保留现行规则、历史记录和引用关系。
- 是否将未知技术路线或业务选择误写成既定结论。

内部攻击防护参考仅核实受众及版本管理边界，未复制其防护正文。审查者未运行应用测试、迁移或外网技术调研，未修改任何文件；本记录由主代理另行创建，提案保持被审查版本原样。

## 2 总体意见

提案总体方向合理，可以交人工审核。它明确保留现有分层与需求，不以旧实现反推新设计；将调研、历史审查、规范和待决事项分开也有依据。

**不建议直接按“批准全部结构项 P01–P21”执行。** P 集合实际混合结构整理、语义修正及待裁决工作的落点，需要明确批准粒度和依赖。

未发现必须撤回整份提案的严重问题；发现两项中等风险及三项需要澄清的低风险问题。当前结论仅针对方案，不代表现行设计已经一致，也不代表重新实现条件已经满足。

## 3 审查发现

### R01 中等风险 P 集合不能整体作为结构调整批准

涉及提案第 4、7 章，P08、P10、P12、P13、P15、P16，以及 C01–C08、D01–D08。

第 7 章将 P01–P21 称为“结构”集合，但其中包含：

- P08：修正 P35 的 Review 版本刷新行为，依赖 C03 和 D03。
- P10：补人工确认门槛、调整 Review 刷新路径，涉及 D01、D02、D04。
- P12：取消同步失败发布豁免，对应 C02。
- P13：改变 SQL 默认值、迁移上下文字段，对应 C01 和 D08。
- P15：调整验收分期及诊断权限，涉及 C06、D03。
- P16：修改容量估算和发布检查，涉及 C07 及能力分期。

这些均不只是移动文件或增加导航。虽然提案已声明“结构批准不自动批准语义修改”，但审批集合本身仍容易产生歧义。

建议保留 P 编号作为逐文件影响清单；另按结构、明确对齐、待决细化标记每个具体动作及其依赖。批准某个 P 文件项时，必须列明动作范围，不能自动批准该行关联的 C/D 内容。

本次仅记录建议，不调整提案。

### R02 中等风险 SQL 中独立 enabled 字段的语义冲突尚未明确列入计划

涉及 P13、C01、D08。

依据：

- [02 领域](../design/02_domain_core.md)第 4 章明确“不存在独立的检索词 enabled 领域状态”；手动构建使用本次 SelectedSearchTerms，自动构建使用 auto_update_enabled。
- [SQL 草案](../design/07_data_schema.sql)的 search_terms 同时包含 `enabled boolean not null default true` 和 auto_update_enabled。

提案已准确识别 auto_update_enabled 默认值错误，却未明确列出旁边 enabled 字段的问题。仅改默认值后，后续实现者仍可能使用 enabled 作为额外过滤条件，形成领域未定义的第三套选择机制。

建议在未来修订提案时，将该字段纳入 SQL 与领域映射核对。说明它是否只是无业务用途的历史草案字段；若无现行依据，提出移除或替代映射建议。不得在本次审查中直接删除，也不能简单把它改名为 selected，因为手动选择属于本次运行输入。

关闭条件：明确检索词持久配置与单次 Run 选择快照的对应关系，保证手动和自动构建各自只有已定义的选择规则。

### R03 低风险 应明确拆出线框后的现行 UI 规范身份

涉及第 2、3 章，P01、P08。

依据：[03 UI](../design/03_ui_workspace.md)第 9 章不仅包含示意图，还包含权限、只读、对象切换、知识资产边界和交互说明；P13 线框后的正文承载当前 Workspace Shell 的具体行为。第 10 章则是历史审查，两类内容性质不同。

提案正确区分了两个目标文件，但职责规则将“线框”与“SQL 草案、速查、调研、历史审计”并列，容易让读者误认为整个线框子文档都只是无规范作用的参考。

建议明确 appendices/ui_wireframes.md 是 UI 规范的组成部分，受 FR/Domain 约束，不能新增或覆盖业务规则；reviews/ui_review_2026-06-01.md 才是历史证据。将具体交互规则保留在附录还是收回主文，也应有统一约定，避免拆分造成要求降级或重复维护。

### R04 低风险 领域状态权威与 FR017 明示职责需要进一步区分

涉及第 3 章第 3 条，P06、P10、D05。

依据：提案规定“领域合法状态归 02，执行与锁机制归 05”；[FR-017](../design/01_functional_requirements.md)明确将内容保护的“具体状态转换和冲突处理”交给 05；[02 领域](../design/02_domain_core.md)已承载内容保护不变量和 Run/Session 生命周期。

二者可以兼容，但当前职责概括还不足以避免未来把所有状态转换都迁入 02，或让 05 独立改变领域允许的行为。

建议补充区分：02 定义状态含义、合法性及不可破坏的不变量；05 按 FR-017 定义命令触发的内容状态转换、校验顺序、冲突响应和执行流程。遇到规则重复，引用唯一来源，而非重新制定一套状态机。这属于职责表达澄清，不必据此改需求。

### R05 低风险 附录迁移验收应覆盖文本引用与章节定位

涉及第 2、7 章，P02、P03、P08、P20。

依据：03 第 2 章直接引用“第 9.2 节”，并非 Markdown 链接；线框正文、历史审查和变更记录通过 P 编号相互关联；[00-00](../design/00-00_layer_design_file_mapping.md)现行维护规则只允许登记顶层设计文件；013 拟迁移后仍保留旧入口。

提案已有链接和引用检查要求，但执行时仅检查链接目标存在，不足以保证文本中的章节号、旧锚点和目录规则仍有效。

建议未来执行清单明确检查 Markdown 链接、纯文本章节引用、P 编号、旧路径入口、目录“仅顶层”规则及相对路径变化。历史内容保持原义，必要的路径变更加迁移说明，避免追改历史结论。

### D04 的补充证据与影响范围

[FR-034](../design/01_functional_requirements.md)明确：“用户确认最终稿后，系统生成可导出版本。”

此外，FR-019 要求导出已经生成并确认的 Review 可导出版本；FR-035 要求记录最终稿确认状态。02 第 8 章规定终稿默认 accepted，第 10.1 节、领域事件及覆盖检查也引用默认接受语义。

因此，D04 不应只核对 P28 按钮与 Domain 第 8 章。最终裁决需要同步核对 FR-019/034/035、Domain 第 8/10/12/13 章，以及 UI、应用流程、API、数据和测试入口。

本审查不选择“人工确认”“默认接受”或“双状态”中的任何方案；“双状态”目前只是讨论方向，尚无足够证据证明现行文档已采用该模型。

## 5 建议人工审核时明确的事项

除提案已有 D01–D08 外，建议明确：

1. 批准粒度：P 项作为文件影响索引，还是拆成可单独批准的动作；语义修改应列明对应 C/D 依赖。
2. 附录身份：拆出的现行 UI 交互要求继续作为规范组成部分，历史审查保持历史性质。
3. D04 裁决范围：不仅决定是否显示确认按钮，还要决定终稿、接受、可导出版本之间的状态和权限关系。
4. SQL 字段冲突处理：将 search_terms.enabled 明确纳入后续提案修订或 D08 细化，不能遗漏。

以上是供人工选择的建议，没有新增已经生效的需求或规则。
