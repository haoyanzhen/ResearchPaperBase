# API 边界再设计：引用、稿件编辑与资产入库

文档版本：v1.1
更新日期：2026-10-16
状态：R1-A、R2-A、R3-A、R4-A及补充决定已于2026-10-16采纳；第11节为现行裁决，前文保留提案评审原貌，不能覆盖第11节及已同步规范。不构成代码实现或验收结果。

## 1. 本轮目的与权威边界

用户要求：引用遵循学术规范，不引入段落覆盖率/豁免等过量检查；重新评估终稿快照和本地/文本框编辑，必要时只下载编辑；有意清空允许发布版本，所有已有论文关联删除均提示风险后允许；已入库论文不能改，未入库可改，入库后改走删除—新导入。用户要求先由 subagent 再设计，形成方案供人工评审。

本提案记录这些明确意见，并将其转为可审查的流程；未批准的具体选择不能先写成现行规则。原 API-E01–E04 推荐方案不再是当前推荐，仍留在[历史工作单](../workorders/api_p0_design_review_2026-10-16.md)供追溯。此前已采纳 D03/D06 等规则的替换范围在本文显式列出，批准后再同步规范。

当前基础：[需求](../design/01_functional_requirements.md)、[领域](../design/02_domain_core.md)、[知识版本与引用](../design/02-02_construction_versioning_appendix.md)、[资产流程](../design/02-03_construction_assets_appendix.md)、[API](../design/04-01_p0_operation_contracts.md)、[应用编排](../design/05_application_use_cases.md)。新近确认的不可变知识版本、物理资产复用、旧引用解析及用户版本选择保持不变；不能把“无需综述导出快照”理解成允许修改已发布知识版本。

## 2. R1 引用：明确学术规范，不计算覆盖率

### 问题

引用是否恰当取决于陈述、来源及支持关系，不能由段落数量或文献数量决定。现有 strict_citation_coverage、充分/不足状态和此前豁免方案会把数量检查冒充学术判断。

### 推荐方案 R1-A

写作与审查遵循以下规则：

- 借用他人观点、数据、方法、文字或图表时，应清楚标注来源；连续叙述的来源清楚且未改变时，不要求每句或每段重复引用。不设置引用数量配额或免引用申请。[APA 引用适度原则](https://apastyle.apa.org/style-grammar-guidelines/citations/appropriate-citation)
- 引用应支持相关陈述；尽量核对原始来源，元数据准确，正文与参考文献表对应；已知撤稿、更正及预印本状态如实呈现，格式服从目标刊物。ICMJE 属于医学领域，此处借鉴一般引用原则，不把其排版规则强加给所有学科。[ICMJE 参考文献建议](https://www.icmje.org/recommendations/browse/manuscript-preparation/preparing-for-submission.html)
- 产品要求：直接引文准确标示并保留可用定位；只使用摘要时明确来源，不宣称核验全文；作者自己的推论和研究设想与来源事实区分。P0 提供一致编号引用和完整参考信息，不新增样式配置平台。

检查仅复用两层现有能力：

| 层次 | 做什么 | 不做什么 |
| --- | --- | --- |
| 机械完整性 | 文内标记、参考条目、证据身份/版本/定位的对应检查；复用现有引用解析及权限 | 不给引用充分率，不替代科学判断 |
| 章节审查/全文终审 | 对可能缺来源、支持不足、误引给出位置与建议，由用户处理 | 不靠 Agent 分数阻断确认，不新增逐句审批 |

保存人工正文不因学术建议或坏标记而失败；正文保留，问题明确显示，不把坏标记注册为有效 EvidenceRef。越权、跨 Project/绑定版本的证据访问和伪造关联仍硬性拒绝，系统不得从不可读证据读取并注入内容；人工输入文字不要求反查其出处权限。旧修订审查不冒充当前稿审查。无问题只显示“未发现引用链接问题”，不显示“学术规范已全面通过”。

**删除** strict 开关、citation-policy 端点、coverage sufficient/insufficient/unknown、阈值与豁免；**保留** EvidenceRef、动态解析状态、ReviewIssue、内容修订和审查历史。UI 改为“引用与审查问题”。

替代 R1-B：保留只检查引用链接完整性的严格开关，不再称覆盖率；仍增加一套配置与确认分支，收益有限，不推荐。

**需批准的变化：R1-A 替换 D03 A 的严格覆盖产品能力及 FR-033 相应阻断规则；保留其确定性机械校验原则。** 学术规范不是本系统自动认证承诺。

## 3. R2 终稿：简单写入框与下载，取消独立导出快照

### 问题与方式比较

现有终稿 PATCH 已能保存 Markdown；复杂度主要来自“编辑后快照过期，再生成快照”的第二套业务生命周期。网页写入框可行，无需把编辑能力与用户电脑文件系统绑定。

| 方式 | 设计判断 |
| --- | --- |
| 网页正文写入框 | 推荐；受控读写 API、revision 防覆盖、普通安全预览即可 |
| 服务器托管文件直接改 | 可以作为内部存储，但仍需权限与一致性；不暴露路径写接口，不比受控正文保存更简单 |
| 直接修改用户磁盘文件 | 当前多用户 Web 设计没有本地授权/同步契约，P0 不增加这套集成 |
| 下载后本地编辑 | 推荐作为完成后路径；外部改稿不自动同步回平台 |

### 推荐方案 R2-A

1. 终稿生成成功，当前稿默认 accepted，Run 仍可继续；大纲和必需章节确认仍是首次汇总前置。
2. 提供单一 Markdown 正文编辑区与保存按钮。完整文章为唯一可写正文；摘要/关键词/参考文献若单独投影显示，必须由同一修订派生，不能另存一份与正文冲突的可写稿。
3. 仅 Run 可继续且稿件 accepted 时允许编辑；保存不会使 rejected 自动恢复接受或下载资格，后续生成新结果沿用既有规则。保存携带 expected_revision，成功即为当前可读、可下载稿；修改人、时间、人工来源、修订继续记录，不生成独立可导出快照。旧审查提示为“对应旧稿”，不要求为了下载重新调用模型。
4. 新生成或重新生成结果先独立完成，再按原 revision 和人工覆盖授权提交；失败或迟到结果不覆盖已保存稿。只是不保存每次编辑的完整历史，不删除已有独立 accepted 终稿成果。
5. 用户显式“完成综述”：无活动任务，当前稿 accepted，来源大纲/必需章节未被后续变更使其失效；原子检查 Run/稿件/来源修订后 succeeded。终审建议可以保留；完成不是接受或下载的前置。仅编辑终稿不会反向使章节确认失效。
6. 完成后平台只读；继续修改就下载本地编辑。P0 不新增 reopen、复制 Run 或本地回传。也可在完成前随时下载已保存稿。

“写入框”指普通正文编辑器。自然语言请求 Agent 改写仍属于生成/建议流程，须遵守已有人工覆盖保护。

**保留**知识版本不可变快照、稿件 revision、权限、任务写资格、最小追溯；**移除**P0 ReviewExportableVersion/ExportableSnapshotView 独立生命周期、current_exportable_status/matching_exportable_version_id、exportable-versions 读写端点及“重新生成快照”按钮。P1 异步格式转换仍须固定那次任务的输入，属于内部执行一致性，不要求用户先创建快照。

最小新增契约提案：

- `POST RV/complete`：Run expected_revision、final_id、final_revision，检查来源集合；使用既有幂等与状态冲突协议，不新增接受确认 token。
- `GET RV/finals/{final_id}/download?expected_revision=...`：鉴权读取指定当前修订，一次一致读取形成 Markdown 附件；不匹配返回 **412**（沿用公共修订协议），不悄悄下载更新稿，不调用模型。不保留任意旧修订下载 API；下载开始后固定所读内容，后续保存不混入同一流。
- rejected、deleted、越权均不能下载；attachment/no-store/nosniff，预览不执行脚本。已下载副本不能远程撤回；平台不自动跟踪外部编辑。

**分期变化需批准：P0 增加单篇已保存稿 Markdown 下载；通用导出中心、批量导出、PDF/Word 转换仍为 P1。R2-A 替换已采纳 D06 A；保留 D05 的显式完成方向，撤回旧 E02 关联新 Run 的推荐。**

替代 R2-B：不提供平台终稿编辑，只下载本地修改。它会删减 FR-034 已有编辑需求，且仍需章节编辑/并发保护，不因假设安全风险而默认选择。

## 4. R3 关联删除与清空：风险提示后允许，发布后生效

### 用户已明确的方向

单条、多条及全部删除都是 Project 关联移除，应提示风险后允许；有意清空可以发布版本。不重复询问是否允许清空，也不把旧引用依赖当作删除否决条件。

### 推荐交互 R3-A

选择范围 → 一次风险预览及确认 → 自动受理移除型 Construction → 显示待移除/运行状态 → 发布成功后新版本生效。风险说明只需清楚表达：

- 后续新版本将不再包含选定成员；已绑定旧版本的研究和引用仍保留，关联移除不等于物理删除旧文件。
- 列出实际关联范围和已知依赖，未知影响不冒充无影响；删除全部论文但还有资料不算空知识库。
- 真正清空后默认版本为空，需导入资料或显式选用可访问的非空历史版本开展有证据的新研究。

确认绑定具体资产集合及修订，排队期间新增资产不会自动加入“全部”范围；目标修订/范围变化则提示刷新确认，不能授权扩大删除。已完成同一移除重复请求返回既有结果，不重复执行。

仍由 Construction 唯一发布；确认后只是可靠受理，不立即把正式资产隐藏并宣称成功。失败/取消保留原默认版本及诊断，不能把部分移除作为完整成功。

**与活动构建竞争（待评审的具体执行策略）：** 无冲突则按已有槽规则排队；若当前构建准备发布被删目标，预览明确告知会使其相关发布依据失效、需要终止该冲突构建后执行移除。建议同一次删除确认同时授权这个已列明的安全终止，撤销旧写资格再让槽，不再要求用户手动完成第二套取消流程。预览后新出现的冲突任务不在原授权内，刷新影响预览，不静默取消未展示的运行。无关研究、综述和无冲突构建不取消。这是交互及冲突策略提案，不等于现行自动取消授权。

有意全排除成功形成新的空 KnowledgeVersion，结果为 published，默认指针切换；空关系/索引/图谱视图仍须完整一致。检索失败、解析失败和零新增不属于这一例外；后续导入基于空版本继续。新版本不能改变旧引用绑定，物理清理仍走独立已有授权路径。

**空版本使用建议（仍需评审）：** 空版本可浏览，不在其上新建有证据 Research/Review；显示导入或显式选非空历史版本入口，不暗中回退默认版本。旧对象继续其旧绑定。

替代 R3-B：确认仅创建待移除请求，由用户以后统一启动构建；技术上可行，但操作未完成的认知成本高。发布时点和历史保留原则不变。

## 5. R4 论文编辑截止与删除后新导入

### 用户已明确的方向

未入库论文可改，已入库论文不可改；需要修改时删除项目关联再重新导入。现行设计虽已禁止原地改旧版本，却还允许 metadata_correction/text_supplement/analysis_revision 发布新的同条目修订；这不足以满足本次更严格要求，须收窄这些入口。

### 编辑截止建议 R4-A

| 阶段 | 用户能做什么 |
| --- | --- |
| 入库确认受理前 | 修改候选元数据、文件/文本、分析及评分/有效性；依赖变化使相关处理与确认失效，活动处理不能与编辑竞争 |
| 入库确认已受理、后台隔离写入/发布中 | 本批候选锁定，不继续编辑；旧执行不得使用新内容冒充原确认 |
| 发布成功 | 已入库内容只读；可移除关联，需改内容则移除成功后重新导入 |
| 入库失败且未发布 | 保留人工草稿与失败诊断；P0 可在新构建准备候选，不新增原 Run 的 P0 恢复入口；既有 P1 恢复仍按冻结依据执行 |

这把产品编辑截止线定为“确认入库已受理”，正式可供研究使用仍以成功发布为准。不用数据库某行第一次写入作为用户可见时点。

替代 R4-B：直到发布前均可撤销确认、撤销执行资格并重整隔离产物后再编辑；更灵活，但引入额外恢复与并发处理，P0 不推荐。

已入库的不可改范围包括项目内元数据、原文件/正文、解析文本、分析、评分/有效性等知识内容。权限、当前可用性、已知风险与推送状态属于独立运行投影，不是改论文内容，继续按既有规则更新。全局论文身份和其他 Project 不随移除而改变。

### 删除—新导入的具体行为

- 推荐先发布移除，再显式新导入，不新增“原子替换论文”的 P0 命令。两次发布之间该论文不在最新版本中，旧版本仍可读；这一代价必须显示。
- 同 DOI 仍使用同一 PaperIdentity；可保留 Project 逻辑身份，以新入库内容修订形成成员，不制造第二个全局论文身份或重复活动成员。
- 当前版本尚包含该论文：导入提示先移除，不能暗走已发布修订接口。已经移除：显式导入可重新纳入，提示曾被排除，重新确认新内容。
- 自动检索再次命中不得恢复人工排除；只有本次用户明确重新纳入才能解除对应排除决定。
- 允许安全复用不可变文件字节，不继承旧人工确认或用旧分析假装已分析新内容；旧引用始终指向原修订。

**范围建议需批准：** 对 ProjectMaterial 采用同样入库后只读/删除—新导入规则，避免两种资产规则不同。用户本次直接提到论文，因此资料范围不默认为已授权。

### 原“返回检索字段”问题不混同论文编辑

用户此次明确的是论文内容修改边界，并未直接决定检索词、时间窗、来源和预算可改哪些。建议最小方案仍为：同 Run 在筛选等待点追加已确认检索词，来源/时间范围/预算/基线不变，使用剩余额度；入库确认后不返回检索。需改范围或额度则新建构建。此建议单独交评审，不借“未入库可编辑论文”推导任意改运行配置。

## 7. Subagent 预案与主审取舍

- citation_redesign：独立核对需求/领域/API，并核验 APA、ICMJE；采纳取消覆盖率与 strict 能力的建议，明确这是待批准的 D03 替换。
- review_edit_redesign：比较四种编辑方式；采纳轻量编辑+完成后下载，保留 D05、替换 D06；把下载修订失配统一为现行公共协议的 412，不新增 409 变体。
- asset_lifecycle_redesign：识别已发布 pending revision 与用户新要求的实质冲突，区分入库三个时点、自动排除与显式重新纳入；采纳确认后锁定和两次发布方案，不新增 P0 失败原 Run 恢复。
- 主审补充：风险预览与一次确认、活动构建冲突终止的授权范围、空版本消费、ProjectMaterial 范围和原返回检索字段均显式列为评审选择，不能由代理审查替代人工决定。

## 8. 后续验收场景（未执行）

1. 连续陈述来源清楚时不要求逐句重复引用；原创推论无豁免申请，不显示覆盖率。
2. 引用可解析但不支持陈述时，只给具体审查建议，不声称科学正确；坏标记不丢正文，越权证据不进入稿件。
3. 终稿保存后即能读取/下载同一修订，无快照按钮；两窗口冲突保留用户输入，迟到任务不覆写。
4. 完成与编辑/任务启动竞争按修订和状态裁决；完成后只读，下载不混入后续修订；拒绝/越权稿不可下载。
