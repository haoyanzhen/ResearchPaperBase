为什么同一 Research Session 内一次只允许一个流式回复追加？

```markdown
因为同一个 `Research Session` 的对话历史是有顺序的。如果同时允许两个流式回复写入同一个 Session，会出现几类实现和体验问题：

- **消息顺序冲突**：用户连续发出 A、B 两个问题，如果两个 Agent 同时流式回复，系统很难保证最终历史是 `A -> answer A -> B -> answer B`，还是交错成不可理解的顺序。
- **上下文基准不一致**：第二个回复应该基于哪些历史？如果第一个回复还没完成，第二个回复是否能引用它？这会导致上下文不确定。
- **流式内容交错**：两个 SSE/WebSocket 流同时追加到同一对话，前端容易出现 token 交错、引用错位、结束状态覆盖等问题。
- **引用追溯混乱**：每个回答都有引用论文、文段和图谱节点。如果两个回答并发写，引用可能绑定到错误的轮次。
- **取消/失败语义复杂**：如果用户取消其中一个回复，另一个是否继续？如果一个失败，是否影响 session 状态？会明显增加状态机复杂度。
- **数据库写入竞争**：同一个 session 的 `turn_index`、message append、summary update、last_active_at 等字段容易发生竞争。

所以这里的限制不是说用户不能开多个研究任务，而是：

- 同一个 `Research Session` 内，一次只允许一个 active reply stream。
- 用户如果想并行探索，可以创建多个 `Research Session`。
- 同一个 Project 下可以并行多个 Research Session。
- 每个 Session 内保持线性对话顺序。

这个设计相当于聊天产品里的常见规则：一个 chat thread 一次只生成一个 assistant reply；并行研究通过新建 thread/session 实现。
```

这会造成实现上的混乱。比如用户今天修改了检索词，那么昨天那次自动推送到底用了什么检索词？如果失败重试，是按旧配置重试，还是按新配置重试？如果邮件被投诉推送错误，系统如何追溯当时的配置快照？

所以配置对象和执行对象应该分开。

**推荐对象模型**
| 对象 | 数量 | 作用 |
|---|---:|---|
| `Project` | 每课题 1 个 | 长期研究容器 |
| `Construction Workspace / Plan` | 每 Project 1 个 | 保存构建模式长期配置 |
| `Search Term` | 每 Project 多个 | 保存检索词、启用状态、自动更新状态、数据源选择 |
| `Construction Run` | 每次执行 1 个 | 保存一次手动/自动构建的配置快照、状态、结果 |
| `Knowledge Version` | 每次成功构建 1 个 | 保存一次成功构建后的可检索知识库版本 |

用户层面可以表现为“每个 Project 只有一个构建模式页面”。但系统层面仍应有多条 `Construction Run` 历史记录。

**2. 自动推送是不是系统级配置**
调度器是系统级的，但“要不要跑、跑什么、怎么跑”不是纯系统级。

更准确是三层：

- 系统级调度器：什么时候扫描，是否启用后台任务，最大并发，每次扫描多少 Project。
- Project/Construction Workspace 级配置：这个 Project 是否参与自动更新，默认策略是什么。
- Search Term 级配置：这个检索词是否参与自动更新，使用哪些数据源，是否启用。

所以自动推送不是“Project 级调度器”，但也不是“只有系统级配置”。它应该是：

**系统级 scheduler 读取所有 Project 的 Construction Workspace 配置，然后为符合条件的 Project 创建 Construction Run。**

这点很重要。系统负责调度，Project/Workspace 负责意图，Run 负责执行记录。

**3. 检索词和数据库配置应放在哪里**
你的想法是合理的：检索词生成阶段应该允许用户添加、删除、启用、禁用检索词，并配置其是否参与自动更新。

我建议最小版这样做：

- 每个 Project 的 Construction Workspace 保存所有检索词。
- 每个检索词有 `enabled`。
- 每个检索词有 `auto_update_enabled`。
- 每个检索词可以选择适用数据源，或者先简化为使用 Project 默认数据源。
- 用户可选择一个或多个检索词手动重新构建。
- 自动任务只选择 `enabled=true` 且 `auto_update_enabled=true` 的检索词。

如果要控制复杂度，第一版不要做“每个检索词独立阈值、独立时间范围、独立最大数量”。先做：
- Project 级数据源集合。
- Search Term 级是否参与自动更新。
- Run 启动时生成配置快照。

**4. 数据库版本管理应该如何改**
如果采用“一个 Construction Workspace + 多个 Construction Run 执行记录”，知识库版本边界会更清晰：

- `Construction Workspace` 不生成 Knowledge Version。
- 每次 `Construction Run` 成功后生成一个新的 `Knowledge Version`。
- `Research Session` 和 `Review Run` 绑定某个 `knowledge_version_id`。
- 自动构建产生的新 Knowledge Version 不打断 active Research Session / Review Run。
- 已完成内容不自动改写。
- 新建 Research Session / Review Run 默认使用 Project 当前默认 Knowledge Version。

这样比“唯一 Construction Run 覆盖自身结果”更可靠。因为 Knowledge Version 是执行产物，不是长期配置对象。

**5. 用户体验上可以隐藏多 Run**
你担心多个构建 run 让用户困惑，这个担心是对的。但解决方案不一定是删掉 run，而是不要把历史 run 当成主入口暴露给用户。

用户看到：
- 一个“构建模式”页面。
- 一个检索词与自动更新配置区。
- 一个“立即运行构建”按钮。
- 一个“最近执行结果”区域。
- 一个“历史执行记录”折叠列表。

系统内部保留：
- 每次手动构建 run。
- 每次自动构建 run。
- 每次 run 的配置快照。
- 每次 run 的状态、错误、产物和 Knowledge Version。

这比“只有一个 run，不断覆盖”安全得多。

**结论**
你提出的“不要让用户管理多个构建 run”是对的；但“系统里完全不要多个 Construction Run”不建议。

最佳模型是：

**每个 Project 一个 Construction Workspace，里面管理检索词和自动更新配置；每次手动或自动执行生成一个 Construction Run；成功 Run 生成 Knowledge Version。**

这既符合用户心智，也保留了实现所需的审计、幂等、失败恢复和版本管理能力。

**手动上传论文的元数据解析**

[01_functional_requirements.md](docs/design/01_functional_requirements.md)  中的FR-018 论文补充与手动上传 中系统自动解析论文元数据，应该也是一个单独的LLM调用函数？

```markdown
是的，我建议把 FR-018 里的“系统自动解析论文元数据”明确成一个独立的 LLM 调用函数，但它不应该是唯一手段。

更合理的边界是：

1. 先走确定性解析  
   DOI、arXiv ID、URL、PDF 内嵌 metadata、标题页文本、Crossref/OpenAlex/Semantic Scholar 等外部 API 查询。

2. 再走独立 LLM 结构化抽取函数  
   当上传的是 PDF-only，或者规则/API 解析不完整时，调用类似：

   `extract_paper_metadata_with_llm(input_text, file_context) -> PaperMetadataDraft`

   输出应是结构化草稿，例如标题、作者、年份、venue、DOI、arXiv ID、摘要、关键词、置信度、缺失字段、证据片段。

3. 最后进入人工确认  
   LLM 抽取结果只能作为“待确认元数据”，用户确认或补充后才能进入去重、解析、分析、入库流程。

我建议在 [docs/design/01_functional_requirements.md](/Users/qingyue/projects/ResearchPaperBase_codex/docs/design/01_functional_requirements.md:836) 的 FR-018 中补一句类似：

> 对 PDF-only 或外部标识缺失的上传内容，系统应先尝试规则解析和外部数据源查询；若关键元数据仍不完整，可调用独立的 LLM 元数据抽取函数生成结构化元数据草稿，并标记置信度与证据来源，供用户确认或修改后继续流程。

这样职责会更清楚：FR-018 负责“补充/上传入口和确认流程”，LLM 元数据抽取是其中一个可复用能力，不和 FR-019 的 PDF 全文解析、FR-020 的论文 AI 分析混在一起。
```

正常情况下，在用户无外部输入，仅上传一篇pdf时，应该是无法获取外部 API 的，对吗？这里的第一步是什么意思呢？

> 对，你这个理解是对的：如果用户只上传一篇 PDF，且没有提供 DOI、arXiv ID、URL、标题等外部输入，系统一开始通常不能直接调用外部论文 API 做可靠查询。因为外部 API 查询至少需要一个检索锚点，比如 DOI、arXiv ID、标题、作者组合等。
> 所以 FR-018 里应避免写成“上传 PDF 后先查外部 API”。更严谨的流程应该是：
> PDF-only 上传时，系统先从 PDF 文件本身提取候选元数据；若提取出 DOI、arXiv ID、标题或作者等可查询锚点，再调用外部数据源补全与校验；若本地解析和外部补全后关键元数据仍缺失，可调用独立 LLM 元数据抽取函数生成待确认草稿，并要求用户确认或补充后继续。
